# 04 — Envelope and franking

## Envelope

Every application message in a `text` or `interaction` group is one **envelope**, the MLS
`PrivateMessage` application data. Deterministic CBOR, fixed-position array of 9 elements:

```
[
  v,             ; uint, = 1
  msg_id,        ; bstr, 16: random, chosen by the sender; edits/deletes/reactions reference it
  type,          ; uint: 0 message, 1 edit, 2 delete, 3 reaction add, 4 reaction remove, 5 pin, 6 unpin
  thread_id,     ; bstr 16 or null: the msg_id that roots the thread this belongs to
  reply_to,      ; bstr 16 or null: for type 0 the message replied to (or null); for types 1..6 the target msg_id, never null
  body,          ; tstr: markdown for type 0/1; the emoji for 3/4; empty for 2/5/6
  attachments,   ; array of [blob_id (bstr 32, SHA-256 of the stored bytes), key (bstr 32), nonce (bstr 12),
                 ;           size (uint, plaintext bytes), mime (tstr), w (uint|null), h (uint|null),
                 ;           thumb (bstr|null: the sealed thumbnail, § Attachments), name (tstr: the file's name)]
  previews,      ; array of [url (tstr), title (tstr), description (tstr), image (bstr|null)]
  k_f            ; bstr, 32: the franking key, random per envelope (also per edit)
]
```

Limits: `body` ≤ 4 000 UTF-8 bytes for type 0/1; ≤ 32 bytes for type 3/4; **0 bytes for type
2/5/6**. At most **4** attachments; at most **2** previews. In an attachment: `mime` ≤ **255**
bytes, `name` ≤ **255** bytes, `thumb` ≤ **8 192** bytes. In a preview: `url` ≤ **2 048** bytes,
`title` ≤ **256** bytes, `description` ≤ **1 024** bytes, `image` ≤ **16 384** bytes. An envelope of
type 1 to 6 names its target: its `reply_to` is not null, and its `attachments` and `previews` are
empty. A receiver rejects an envelope over any limit (`E_ENVELOPE_LIMIT`), of the wrong length or
breaking the type 1 to 6 rule (`E_ENVELOPE_SHAPE`), or with an unknown `type` (`E_ENVELOPE_TYPE`); it
MUST NOT render a partially valid envelope.

On a **server-readable channel** (`09-http-api.md` § Readable channels) the instance stores the
envelope in the clear and keys each message by the channel's own `seq`, not by `msg_id`. There, an
envelope's `reply_to` and `thread_id` carry the target's channel `seq` as a big-endian uint64 in the
low eight bytes, with the high eight bytes zero; in an end-to-end encrypted group they carry the
target's `msg_id` unchanged, because there the server has no key to resolve. The element's shape
(a 16-byte `bstr` or null) is the same in both.

## Attachments

An attachment is a file the sender encrypts on its device and uploads as an opaque blob (`09` §
Blobs). The envelope carries everything a receiver needs to fetch and open it; the instance learns
the blob's size and the channel it was stored for, nothing else.

- **Key and nonce.** The sender draws `key` (32 bytes) and `nonce` (12 bytes) at random for every
  attachment and never uses them for anything else.
- **The file.** `stored = AES-256-GCM(key, nonce, aad = "dilla attachment v1", plaintext = the
  file)`, written as the ciphertext followed by the 16-byte tag and nothing else: the nonce travels
  only in the envelope. `size` is the plaintext's length in bytes; `blob_id = SHA-256(stored)`.
- **The thumbnail.** Optional, for an image. Its plaintext is a WebP image (a JPEG where the
  sender's platform cannot encode WebP) whose longest side is at most 320 px and whose length is at
  most 8 176 bytes; `thumb = AES-256-GCM(key, thumb_nonce, aad = "dilla thumb v1", plaintext)`, where
  `thumb_nonce` is `nonce` with its byte 11 XORed with 0x01, so the sealed thumbnail is at most
  8 192 bytes.
- **The name.** `name` is the file's name as the sender gives it (UTF-8, `""` when none). It is
  never a path: a receiver removes control and bidirectional-control characters and path separators
  before it shows or saves a name, and refuses an envelope for a name's length only.
- **Receiving.** A receiver that downloads a blob checks, in this order: `SHA-256(stored) =
  blob_id`, else it refuses the file with `E_BLOB_HASH`; `stored` is at least 16 bytes, opens under
  `key`, `nonce` and `"dilla attachment v1"`, and the plaintext is `size` bytes long, else
  `E_BLOB_OPEN`. A thumbnail that does not open under `key`, `thumb_nonce` and `"dilla thumb v1"` is
  `E_BLOB_OPEN`. A refused attachment is not shown; the rest of the envelope is.
- **Rendering.** `mime` is the sender's claim. A receiver renders a file as an image only when its
  `mime` is `image/png`, `image/jpeg`, `image/webp` or `image/gif`, and a thumbnail only when its
  plaintext begins with `RIFF` and holds `WEBP` at offset 8, or begins with the bytes `FF D8 FF`;
  everything else is a file to save.
- **References.** The sender's client deletes its blob references when it discards a message
  before sending it and when it deletes a message (§ Semantics).

Previews are generated by the **sender**; receivers MUST NOT fetch remote resources for an
envelope.

## Semantics

Types 1 to 6 **fold** onto a target: the message whose `msg_id` their `reply_to` names, in the same
group. A receiver applies the rules below to the rows it holds, ordered by the group's `seq`, and
recomputes them whenever a row they depend on arrives or is deleted, so the outcome does not depend
on the order in which rows reach it.

- **Target.** The target of `X` in a group (in an end-to-end encrypted group; a server-readable
  channel names the `seq`, § Envelope) is the earliest (lowest `seq`) type-0 envelope with
  `msg_id = X` the receiver holds there, shown or deleted. A later type-0 envelope that repeats `X`
  is shown as its own message and is never a target. A fold whose target is not held is kept, not
  shown, and applied when the target arrives.
- **Delete wins.** A type-2 envelope from the target's author (the same `user_id` in the MLS
  credential, from any of the author's devices), or the delivery service's deletion of the target
  (`02` message delete, gateway `message.deleted`), deletes the target: its body, attachments and
  previews are no longer shown, the bodies of its edits are dropped, and its reactions and its pin
  are removed. It applies whichever of the two arrives first. It applies also when the target
  itself is not held: a receiver then drops the bodies of the type-1 envelopes from the same author
  that name the target. A type-2 envelope from anyone else changes nothing. The sender's client also
  asks the delivery service to delete its copy, which the service does only for the uploading user
  (`02`), and deletes the message's blob references.
- **Edit.** Of the type-1 envelopes from the target's author, the one with the highest `seq`
  replaces the shown body. An edit from anyone else changes nothing. An edit raises no mention.
- **Reactions.** A reaction is kept per user and emoji: of the type-3 and type-4 envelopes from one
  user with one `body` on a target, the one with the highest `seq` decides whether that user's
  reaction is present (3) or not (4). A user adds and removes only their own reactions.
- **Pins.** Of the type-5 and type-6 envelopes on a target, the one with the highest `seq` decides
  whether it is pinned (5) or not (6), from any member. This version checks no role snapshot: the
  former rule that a pin needs the channel's pin permission in the receiver's role snapshot is not
  applied, and a client shows who pinned.
- A fold that breaks a rule is ignored, never an error; only § Envelope refuses an envelope.

## Mentions

The body of a type-0 or type-1 envelope may mention someone with the readable syntax of `09` §
Readable channels: `<@` followed by the 32 lower-case hexadecimal digits of a user id or a role id
and `>`, `<@everyone>`, or `<@here>`. A receiver matches the tokens literally (lower-case hex only;
no other spelling is a mention) and counts a type-0 message as mentioning it when the message comes
from another user and carries the receiver's own user id, a role id the receiver holds in that
community, `<@everyone>` or `<@here>`. This version gates neither `<@everyone>` nor `<@here>` on the
`mention_everyone` permission and counts `<@here>` as `<@everyone>`. An edit never raises a mention.
A client shows a mention as the name it stands for, never as the raw token.

## Deterministic CBOR

RFC 8949 §4.2.1 core deterministic encoding: shortest integer form, definite lengths, no maps,
no floats, no tags, no indefinite items. Element order is normative. A receiver rejects
non-minimal encodings and trailing bytes.

**Padding.** The `PrivateMessage` carrying an envelope is padded (RFC 9420 §6.3.1) so that its
total ciphertext length is a multiple of 256 bytes.

## Franking

Franking lets a member report a message so that a moderator can verify what was sent, without the
instance ever reading content and without the reporter being able to forge it.

- **Commitment**, computed by the sender and carried in the `PrivateMessage`'s
  `authenticated_data` (exactly 32 bytes):
  `C = HMAC-SHA256(key = k_f, data = "dilla frank v1" || CBOR(envelope with k_f replaced by an empty bstr))`.
- **Receiver check.** Every receiver recomputes `C` from the decrypted envelope and hard-rejects a
  message whose `authenticated_data` differs (`E_FRANK_MISMATCH`).
- **Tag**, computed by the instance on upload with its per-instance franking key `K_frank`
  (32 random bytes, rotated yearly, old keys kept for verification). The DS reads `C` directly from
  the `PrivateMessage`'s `authenticated_data` — there is no separate `commitment` field on the
  upload — and MUST reject an upload whose `authenticated_data` is not exactly 32 bytes
  (`422 E_COMMITMENT_INVALID`, `02-delivery-service.md`):
  `T = HMAC-SHA256(K_frank, "dilla frank tag v1" || group_id || epoch(8, big-endian) || seq(8) || uploader_device(16) || C || recv_ts(8))`.
  The instance stores `(seq, epoch, uploader_device, C, T, recv_ts)` with the ciphertext and returns
  `T` and `recv_ts` to the uploader.
- **Report.** The reporter submits `(group_id, seq, envelope, k_f)`. The moderator's client
  recomputes `C` from the envelope and `k_f`, the instance recomputes `T` from its stored fields and
  the submitted `C`, and the report is verified only if both match the stored values. The instance
  also recomputes `C` itself and compares it with the `C` it stored, and it recomputes `T` under the
  franking key the message was tagged with, which it records beside the tag (`09` § Reports). Authorship is
  bound through the instance's session-to-device record (an operator attestation, deniable to
  third parties); the report shows exactly the envelope submitted and nothing else.

## Vectors

`vectors/envelope.json` (five envelopes: CBOR bytes, length, commitment), `vectors/franking.json`
(three tags under a fixed instance key) and `vectors/attachment.json` (four attachments: the stored
bytes, `blob_id`, and for one the sealed thumbnail). An implementation conforms when it reproduces
`cbor`, `commitment` and `tag` for every case and `stored`, `blob_id`, `thumb` and both openings for
every attachment, and rejects: the wrong element count; an unknown `type`; `msg_id` or `k_f` of the
wrong length; non-minimal CBOR or trailing bytes; an attachment that is not a nine-element array; an
envelope of type 1 to 6 without `reply_to` or with attachments or previews; and any limit exceeded
(`body` over 4 000 bytes for type 0/1, over 32 bytes for type 3/4, or non-empty for type 2/5/6; more
than 4 attachments; more than 2 previews; `mime` or `name` over 255 bytes; `url` over 2 048 bytes;
`title` over 256 bytes; `description` over 1 024 bytes; a preview `image` over 16 384 bytes; a
`thumb` over 8 192 bytes).

`vectors/envelope.json` also carries a `rejects` array: each entry is well-formed deterministic
CBOR that a conforming decoder must nevertheless refuse, with the `error` code it must refuse it
with. It holds thirteen cases: a delete tombstone with a non-empty body, `mime` at 256, `thumb` at
8 193, five attachments, three previews, a preview `url` at 2 049, `title` at 257, `description` at
1 025, a preview `image` at 16 385 and an attachment `name` at 256 — each refused with
`E_ENVELOPE_LIMIT` — and an edit with no `reply_to`, a reaction carrying an attachment and an
attachment of eight elements, each refused with `E_ENVELOPE_SHAPE`.

`vectors/attachment.json` carries a `rejects` array too: six stored blobs or thumbnails a receiver
must refuse, each with its code — a `blob_id` that does not match (`E_BLOB_HASH`); a flipped tag
bit, a file sealed under the thumbnail AAD, a `size` that disagrees, a thumbnail sealed under the
file's own nonce and stored bytes shorter than the tag (`E_BLOB_OPEN`).

## Error codes

`E_ENVELOPE_SHAPE`, `E_ENVELOPE_TYPE`, `E_ENVELOPE_LIMIT`, `E_FRANK_MISMATCH`, `E_BLOB_HASH`, `E_BLOB_OPEN`.
