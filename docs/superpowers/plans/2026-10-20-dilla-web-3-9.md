**How channels come to exist** (checked for answer 9):
- A community voice channel is a **server-side row only**. `POST /v1/communities/{id}/channels` writes `channels` and overwrites in one transaction, then runs `MaterialiseChannelMembers` (`internal/api/channels.go:476-611`).
- No MLS group exists at creation. A text channel's group is registered later by a client; a voice channel's call group is opened at the first call (`callGroup`, `calls.go:430`).
- Therefore the server can create the AFK channel itself, with no client and no E2EE step. `kind` is not patchable; PATCH changes name, topic, position, parent, mode, visibility and slow mode (`channels.go:735-760`).

## Rulings

They are built as written unless the controller or Jonas overturns them. The source of each ruling is given as (answer N) or (audit id).

### AFK: a built-in listen-only channel (answer 9)

- **R1. Every community has exactly one AFK channel, created by the server.**
  - It is an ordinary `channels` row of kind 1 (voice), named `AFK`, top level, at the last position, with no overwrites.
  - `community_afk.channel_id` points at it. **That pointer is the "built-in" mark.** No new kind is added, so no schema CHECK changes.
  - **New communities:** `Communities.create` (`communities.go:212`) writes the channel and the `community_afk` row (timeout 300) in the same transaction as the community. After the commit it materialises the channel members, exactly as channel create does.
  - **Existing communities:** an idempotent Go backfill, `EnsureAFKChannels`, runs in `dillad serve` after the migrations and before the listener opens.
    - **What counts as done:** a community is done when its pointer names a channel that the backfill itself created. That is recorded as an audit row `channel.create` with a NULL (system) actor and the detail `afk.builtin`.
    - **Every other community, including one whose admin picked an AFK channel in web3.8** (follow-up answer 2):
      1. the backfill creates a **new** `AFK` channel;
      2. it repoints `community_afk` to the new channel and keeps the stored timeout;
      3. the old channel is no longer the AFK destination, so it becomes an ordinary, joinable voice channel with its name and overwrites unchanged.
    - **Release notes** state this per server: a new "AFK" channel appears, and any earlier AFK channel becomes a normal voice channel that the admin may delete.
    
    There is no SQL migration. Random 16-byte ids, the per-dialect SQL and member materialisation all belong in Go, and the backfill re-runs safely on every start.
  - A lazy `ensure` inside `GET /afk` is the backstop for a row the backfill could not write (logged, not fatal).
- **R2. Server-side refusals keep it built in** (authz, opus):
  - `DELETE /v1/channels/{id}` on the AFK channel → `403 E_FORBIDDEN`, "the AFK channel cannot be deleted". Deleting the community still cascades.
  - `PATCH` on it accepts name, position and parent; the parent goes through SRV-CAT's visibility rule. Mode, visibility, slow mode and topic are refused with `403`, so it can never become a readable or text-like channel.
  - `PUT /afk/settings` no longer takes a channel. Its body is `[timeout_seconds]`. A web3.8-shaped body `[channel_id, timeout]` is accepted only when `channel_id` equals the built-in, otherwise `400 E_INVALID_REQUEST`.
  - Timeouts are 60, 300, 900, 1800 and 3600 s, default 300. There is no "off" (follow-up answer 1); auto-move is always on.
  - **No permission overwrites on AFK** (follow-up answer 5). `PUT` and `DELETE` of an overwrite whose channel is the AFK channel return `403 E_FORBIDDEN`, as does a create that names one. Role changes still apply community-wide.
  - **Everyone can always be moved there.** The permission resolver grants every member `view_channel` and `connect` on the AFK channel, whatever their roles, and nothing else: `speak` is irrelevant because the channel is listen-only. The sweep's view and connect check (`afk.go:129-135`) therefore always passes for members. This is an authz change for the opus review.
  - **Existing overwrites:** none are carried over, because the backfill always creates a fresh channel.
  - The refusals sit in the handlers **and** under the community row lock inside the transaction, so a concurrent delete cannot slip past.
- **R3. Listen-only is a property of the AFK channel, enforced in the grant path.**
  - `grantFor` and `admitGrant` (`calls.go:1051-1065`) return `PublishGrant(false,false,false)` for any call row in the community's AFK channel, the same shape as the F11 penalty path.
  - Tokens are minted listen-only, the `/rtc` gate admits only that, and share leases are refused there.
  - The pointer never moves, so there is no grant re-push on change. The web3.8 "live call on pick" case does not exist any more.
  - The `speak` bit is untouched.
- **R4. A move is decided by the server and carried out by the client** (the E2EE constraint: the server cannot add a device to the call's MLS group).
  1. The sweep cuts the device from its source room as today.
  2. It records `afkPending[device]`.
  3. It sends op 54 to that device.
  4. The client reads the `/afk` snapshot, sees `pending` and joins the AFK call itself, arriving listen-only.
  
  A sleeping tab joins when it wakes. The pending entry clears on any join, or after 10 minutes. A failed join shows the dock line "Moved to {channel} for inactivity" with a join button, and never retries in a loop. The occupant roster, `POST /afk` and `DELETE /afk` are retired. Presence in AFK is ordinary room presence, so it survives a restart as calls do (G13).
- **R5. Phones are never auto-moved.** The phone layout (or a coarse primary pointer) sends `exempt = true` as the optional second element of the activity body on its first report after each admission. The server then drops the device from `afkTracked` until its next admission. Desktop browsers keep the in-tab idle heuristic.
- **R6. Muted is shown, not sent.**
  - Every participant of the AFK call is drawn with the `mic-off` glyph (`voice.state.suppressed`).
  - The own mic, camera and share controls are disabled.
  - The stage header hint reads "Everyone is muted in AFK", using the channel's current name.
  - Leaving uses the normal controls. No `voice_state` bit is added.
- **R7. Settings: one row.**
  - Overview → "inactive timeout": 1 minute, 5 minutes, 15 minutes, 30 minutes, 1 hour.
  - Hint: "Members idle in voice this long move to {AFK channel name} and are muted. Phones are not moved."
  - It is part of the overview's one save footer.
  - In channel settings, the AFK channel shows no delete, no mode or visibility controls and no permissions tab, plus one line: "This is the server's AFK channel. Everyone in it is muted."
- **R8. Wire stays 2, with no gateway op** (54 is reused). The changes are:
  - the settings body;
  - `exempt`;
  - the snapshot (adds `pending`, drops the occupant list);
  - `POST` and `DELETE /afk` retired;
  - the new refusal codes.
  
  All are additive or retirements. Each gets a protocol/07 row. Old tabs reload through the build check.

### Layout grammar (S1–S8, reconciled)

- **R9. Tap targets in two tiers, both tested.**
  - **Primary targets on phone or coarse pointers are 44×44:** rows, tabs, header actions, sheet and menu items, call controls, buttons and segmented options. This is today's rule and today's tests; it meets AAA 2.5.5.
  - **Secondary dense targets are at least 24×24 with 2.5.8 spacing:** participant rows, tile chips, inline glyph buttons, and every desktop pointer target.
  - Desktop icon buttons come in 28, 32 and 40 (S5).
- **R10. Row tokens** (S1, answers 2 and 14):

  | Token | Desktop | Phone | Used by |
  |---|---|---|---|
  | `--row-h` | 32 | 44 | channel, voice, thread, admin channel, search result and settings-section rows |
  | `--row-h-sub` | 32 | 36 | voice participants (24 avatar) |
  | `--row-h-2` | 44 | 52 | member rows: 32 avatar with a status corner, name on line 1, line 2 empty until custom status |
  | `--row-gap` | 2 | 0 | between rows |
- **R11. The glyph column is 16 px with `flex: none`** (S2). `#` is centred text, and the other glyphs are 14–16 px monoline icons. Names start at one x in every row type, and participants indent under the names. The lock becomes a 12 px icon after the name (A9).
- **R12. Bars are 48** (S3, `--bar-h`): sidebar head, channel header, members head, stage header (ChannelHeader, C4), settings bar and PhoneHeader. All their hairlines sit at y=48.
- **R13. Every list row ends in one fixed trailing slot** (S4): 32 desktop, 44 phone, always reserved.
  - The slot holds exactly one of: mention pill, unread pill, icon action (join, ⋯), connected glyph, or nothing.
  - The voice count moves after the name (`harbour · 3`).
- **R14. Selected and unread marks** (answer 11): selected is a fill plus the accent bar; unread is a bright name plus a 4 px edge tick. There is no bold.
- **R15. Icon buttons with tooltips replace text buttons outside forms** (S5).
  - New `Tooltip` primitive: mono 11 px, `--surface-hi`, hairline, radius 0, 400 ms on hover and immediate on focus, `aria-describedby`, Esc dismisses, hoverable (1.4.13), KeyHint chord on the right.
  - No tooltip on touch.
  - The accessible name starts with the visible tooltip text (2.5.3).
- **R16. No undefined custom properties** (S6). A unit test fails on a `var(--x)` with no fallback whose token is undefined. It is shown red on `--space-6` and `--focus` first.
- **R17. One settings grammar** (S7): SettingsRow with a 16rem control column, hairlines, and a sticky save footer. On phone the label stacks over a full-width control.
- **R18. List rows get an inset focus ring** (S8): `outline-offset: -2px`.
- **R19. Casing.** Controls and labels are lowercase; headings are sentence case (I4). Discord's terms are used in this casing.

## GIFs (web3.10): GIPHY direct, terms-compliant

This is designed here so that web3.10's brief starts from settled rulings (follow-up answers 3 and 4). Nothing of it is in web3.9.

**Provider status (checked 2026-10-20):**
- Tenor's API shut down on 2026-06-30; new keys stopped on 2026-01-13.
- GIPHY works under these terms:
  - beta keys allow 100 calls an hour; production keys go through an application, with pricing set case by case;
  - "Powered By GIPHY" must be shown where the API is used;
  - requests must come directly from the user's app or browser;
  - media is loaded from the returned URLs and is "not cached, proxied, rewritten, or stored";
  - an analytics pingback (`onload`/`onclick`/`onsent` with a `customer_id`) is "highly recommended".

**Rulings for web3.10:**
- **G1. Off without a key.**
  - The operator sets `[gifs] giphy_api_key` in `dilla.toml`. With no key, GIFs are off: no picker, no GIPHY hosts in the CSP, and no GIPHY request from any page.
  - With a key, GIFs are on for every server of the instance. There is no per-server switch in web3.10.
- **G2. How the key reaches browsers.** GIPHY web keys are client-side by design, so the key is not a secret. It is still served only to signed-in sessions, so anonymous visitors cannot scrape it from the instance.
  - `GET /v1/instance` gains one boolean, `gifs`, and nothing else. It is public and says only that the feature is on.
  - The authenticated `GET /v1/gifs/config` returns `[api_key, rating]`. `rating` is an operator setting, default `pg-13`.
  - The worker fetches it after ready and hands it to the page's picker only. It is never written to the client store or to logs, and is re-read after every ready, so a rotated key takes effect without a reload.
  - No other instance data, user id or device id ever goes to GIPHY.
- **G3. Search goes from the browser straight to `api.giphy.com`, over `fetch` with `referrerPolicy: 'no-referrer'` and `credentials: 'omit'`.** The instance origin, cookies and dilla ids never reach GIPHY.
  - `customer_id` is GIPHY's own `random_id`, fetched once per browser and kept device-local. It is not linked to the dilla account.
  - Pingbacks are sent from the picker only: `onload` for results shown, `onclick` and `onsent`. Viewers rendering a GIF in chat send none, because loading the media already tells GIPHY.
  - At task time the controller checks the current API terms: if viewer pingbacks are mandatory, the controller rules on it, and the release notes say so.
- **G4. What a message holds.** Inside the E2EE body (the ciphertext; the host sees nothing) there is a new optional element, `gif = [id, url, width, height, title]`.
  - `url` is exactly the media URL GIPHY returned for the chosen rendition (`fixed_height` webp or gif), never rewritten.
  - The text body carries the GIPHY page URL, so a client without GIF support shows a link.
  - This is an additive body element, with no envelope, wire or e2ee version change, and a protocol/04 and 07 row. Opus reviews the parser.
- **G5. Rendering on receivers.**
  - A GIF loads automatically for every viewer, as on Discord (answer 4): there is no click-to-load.
  - It loads only if `url` is `https:` on an allow-listed GIPHY media host. The list is the CSP's, verified at task time (for example `media.giphy.com`, `media0`–`media4.giphy.com`, `i.giphy.com`).
  - The image tag uses `referrerpolicy="no-referrer"`, a size reserved from `width`/`height` (no layout shift), alt text from `title`, and "GIPHY" attribution under the image.
  - If the host is not allowed, or the instance has GIFs off (the CSP blocks it), it shows `title` plus the link, never a fetch.
  - Reduced motion: shown paused, with play on focus or hover.
- **G6. No caching or storing.**
  - GIF media is never written to OPFS or IndexedDB, never re-hosted as an attachment, never thumbnailed, and never added to a service-worker cache (the SW, when it exists, passes GIPHY hosts through).
  - Message search indexes `title` only.
  - The browser's own HTTP cache is GIPHY's to control through its headers.
- **G7. The CSP is built from the config at serve start.** It gains `connect-src https://api.giphy.com https://pingback.giphy.com` (verified at task time) and `img-src` for the media hosts **only when a key is set**. A test pins both states.
- **G8. Attribution.** The picker shows GIPHY's "Powered By GIPHY" mark at its foot, monochrome, as GIPHY's marks allow. Every rendered GIF has a small "GIPHY" label. The picker is a tab beside emoji in the composer's emoji button (Ctrl+G), with keyboard navigation over a grid.
- **G9. Privacy statements, stated plainly:**
  - **The picker** shows a footer line: "Searches go to GIPHY, which sees your IP address and what you search for."
  - **Settings → Privacy** has a "GIFs" row: "This server uses GIPHY. When you search, GIPHY sees your IP address and search terms. When a GIF is shown, GIPHY sees your IP address."
  - **For the admin and operator:**
    - a comment above the key in `dilla.toml`;
    - one `dillad serve` startup log line, "gifs: on (GIPHY sees viewers' IP addresses and search terms)";
    - a `dillad doctor` INFO line saying the same;
    - in server settings → overview, a read-only line for server admins: "GIFs are provided by GIPHY on this instance. GIPHY sees members' IP addresses and searches."
  - **`docs/deploy`** gets a GIFs section (key, beta rate limit of 100 calls an hour for the whole instance, the production-key application, what GIPHY sees). **`docs/user`** and the web3.10 release notes carry the same text.
- **G10. Limits and failures.** One key serves the whole instance, so a beta key's 100 calls an hour is shared by everyone. A 429 shows "GIF search is busy, try again later" and is never retried in a loop.
  - Search is debounced (300 ms) and needs at least 2 characters.
  - `rating` is passed to every search.
