# dilla-web-2c — trust and polish Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make contact trust visible and enforceable, then finish local search, settings, diagnostics, typing and voluntary tab hand-over in the self-hosted web client, across two real browsers and a native peer.

**Architecture:** The worker still owns the core, session and gateway. Rust validates leaf credentials and device-list history, keeps TOFU pins and quarantines untrusted message authors; a contentless FTS5 index searches folded local text. Go only relays bounded ephemeral typing and self-state signals after audience checks. The page receives display-safe slices, renders settings and search, and asks the old leader to release its store before a new tab opens it. No secret or plaintext crosses tabs.

**Tech Stack:** Rust 1.98.1 / OpenMLS 0.9.0 / rusqlite 0.40.2 / sqlite-wasm-rs 0.5.5; Go 1.27.0, SQLite and Postgres; TypeScript 5.9.3, React 19.3.0, Vite 7, vitest 3, Storybook 9, Playwright 1.63.0. Existing dependencies only.

**Spec:** `docs/superpowers/specs/2026-09-23-dilla-design.md` (trust, search, settings, accessibility), `docs/design/brief.md` (Mesh copy and layout), `protocol/01-groups.md`, `02-delivery-service.md`, `03-identity.md`, `06-backup-archive.md`, `07-versioning.md`, `08-threat-model.md`, `09-http-api.md`; binding `.superpowers/sdd/2026-10-06-dilla-web-2/facts/rulings.md` E/F and Q05–Q14, Q21–Q24, Q27–Q28; web-2b `progress.md` lessons. ## Interface ledger

Ids continue web-2b's families (CORE 30–39, SQL 30–31, HTTP 80–95, TS 30–38, COPY 03, CI 20–21, E2E 20–21). New signatures are deliberately distinct from the existing ones. A `bstr16` is 16 bytes, `bstr32` is 32, IDs in page commands are 32 lower-case hex characters, and `uint` is deterministic CBOR's unsigned integer.

### Protocol and core

- **L-CORE-40**: For every leaf at Welcome join, external join, staged commit and application message, Rust extracts `CredentialIdentity` and the DSK from the **actual authenticated MLS tree leaf**, verifies both signatures, and compares the authenticated application sender with that same validated leaf. The worker supplies neither credential nor DSK to the trust decision. A merged bad leaf yields quarantine of that leaf/device and `E_CREDENTIAL`, `E_UMK_CHANGED`, `E_DEVICE_UNLISTED`, `E_DEVICE_LIST_STALE` or `E_TIER_MISMATCH`; an Add this device would commit is refused before commit creation. Unknown history leaves the leaf pending and no message body renders. A changed UMK blocks sends in each group still containing that changed leaf until exact-key verification **or a validated Remove eliminates that leaf from that group**; the latter does not approve the new key or unblock any other shared group. A remote member can cause repeated changed-key refusals against an honest sender. The group Remove escape and local quarantine avoid permanent lockout without trusting the attacker. A malicious instance can withhold newer history, including on first sight; TOFU cannot detect that freeze, so the UI must not claim first sight is verified.
- **L-SQL-32**: app schema v4, migrated atomically v1→v2→v3→v4 and v3→v4. `app_device_lists(user_id BLOB PRIMARY KEY CHECK(length(user_id)=16), version INTEGER NOT NULL, list BLOB NOT NULL, umk_pub BLOB NOT NULL CHECK(length(umk_pub)=32), ssk_pub BLOB NOT NULL CHECK(length(ssk_pub)=32))`; `app_trust_pins(user_id BLOB PRIMARY KEY CHECK(length(user_id)=16), umk_pub BLOB NOT NULL CHECK(length(umk_pub)=32), first_seen INTEGER NOT NULL, verified INTEGER NOT NULL CHECK(verified IN(0,1)), changed_umk BLOB CHECK(changed_umk IS NULL OR length(changed_umk)=32))`; `app_quarantine(group_id BLOB NOT NULL, device_id BLOB NOT NULL, code TEXT NOT NULL, PRIMARY KEY(group_id,device_id))`; `app_search_rows(rowid INTEGER PRIMARY KEY, group_id BLOB NOT NULL CHECK(length(group_id)=16), seq INTEGER NOT NULL, body TEXT NOT NULL, terms TEXT NOT NULL, UNIQUE(group_id,seq))` and its indexes are created on **every** backend. In a recoverable savepoint, try `CREATE VIRTUAL TABLE app_search USING fts5(body, content='', tokenize='unicode61 remove_diacritics 2')` plus triggers; on missing FTS5 only, roll back that savepoint, persist `app_meta['search_fts5']=0` and use LIKE. On success store `1`, rebuild the contentless index from `app_search_rows`, and commit. Other SQL failures abort migration. `ClientCore::open` and `migrate_app` use the same capability-aware path, including OPFS. A status-0 type-0 target inserts its folded body, a delete removes it, an edit updates it in the same core transaction. `app_settings` stays the existing table (`schema.rs:176`, `settings.rs:13–54`). No raw untrusted body enters `app_search`.
  The core writes only displayable folded rows to `app_search_rows` in the same unit as the message/fold update; **only when FTS5 exists**, SQL triggers on this folded-body table maintain the contentless FTS table: `AFTER INSERT` runs `INSERT INTO app_search(rowid,body) VALUES(new.rowid,new.body)`; `AFTER DELETE` runs `INSERT INTO app_search(app_search,rowid,body) VALUES('delete',old.rowid,old.body)`; `AFTER UPDATE OF body` first issues that delete command with `old.body`, then inserts `new.body`. A quarantine/delete removes the corresponding auxiliary row and fires the delete trigger. The fallback uses `LIKE` over `app_search_rows.terms` (a leading space plus unicode61-normalized tokens separated by spaces), escaping `%`, `_` and `\`; it never scans raw envelopes. `app_trust_pins` deliberately does not reuse web-2b's message-pin table `app_pins` (`schema.rs:141–143`).

  Capability metadata uses the existing `app_meta(k TEXT PRIMARY KEY,v BLOB NOT NULL)` (`schema.rs:73`) and exact rows `('search_fts5',x'01')` or `('search_fts5',x'00')`, written with `INSERT INTO app_meta(k,v) VALUES('search_fts5',?) ON CONFLICT(k) DO UPDATE SET v=excluded.v`. Run the virtual-table DDL and the three triggers defined above between `SAVEPOINT search_fts5` and `RELEASE search_fts5`; on only SQLite's missing-module error, run `ROLLBACK TO search_fts5; RELEASE search_fts5` and store `x'00'`. A partial virtual table or trigger never survives rollback. Every fresh store and v1/v2/v3 migration creates `app_search_rows` first. The FTS read SQL (bind `:match` to 1–8 escaped `term*` tokens joined with `AND`, `:scope_kind` to L-CORE-42's integer, `:scope_id` to a 16-byte id or null, and `:limit` to 1–50) is:

  ```sql
  SELECT r.group_id, r.seq, r.body
  FROM app_search AS f
  JOIN app_search_rows AS r ON r.rowid = f.rowid
  JOIN app_groups AS g ON g.group_id = r.group_id
  WHERE app_search MATCH :match
    AND g.state <> 4
    AND (:scope_kind = 2 OR (:scope_kind = 0 AND g.target_id = :scope_id)
         OR (:scope_kind = 1 AND g.community_id = :scope_id))
    AND (:before_group IS NULL OR r.group_id < :before_group
         OR (r.group_id = :before_group AND r.seq < :before_seq))
  ORDER BY r.group_id DESC, r.seq DESC LIMIT :limit;
  ```

  The LIKE fallback changes only the FTS match/join into 1–8 escaped `r.terms LIKE '% ' || :term_n || '%' ESCAPE '\'` predicates; the leading space ensures each prefix starts a token. Keep the same scope/cursor/order/limit and a query plan that uses the row limit. The application postfilters each hit against its current folded/displayable state before returning it.
- **L-CORE-41** (new `client/trust.rs`): `pub fn pending_leaves(&self) -> Result<Vec<u8>,ClientError>` returns at most 4096 `[[group_id(bstr16),leaf_index(uint),user_id(bstr16),cached_version(uint),reason(tstr)]]` records for **every current shared-group leaf** on ready (`reason='ready-refresh'`) and for unknown/changed leaves at Q28 boundaries (`reason='unknown'|'changed'`), extracted from actual MLS trees, with no credential or DSK bytes exposed to the worker. `pub fn device_list_ingest(&mut self,group_id:&[u8;16],leaf_index:u32,requested_user:&[u8;16],history_body:&[u8],head_list:&[u8],now:u64)->Result<Vec<u8>,ClientError>` retrieves that exact current MLS leaf inside the core, compares its credential user ID to `requested_user` and **every** signed list user ID, checks the credential against that leaf's DSK, checks entry device ID/DSK/tier against the leaf, validates every list signature and consecutive `prev_hash`, then verifies final signed-list bytes and hash equal `head_list`. New history has 1–1024 versions and ≤4 MiB total; first sight starts at v1, cached history starts from the pinned version; an unchanged exact cached head needs no ingest. 1. The existing `app_settings` table is the storage authority (`schema.rs:180`, `settings.rs:13–54`); web-2c adds only validated keys, not a second settings store. Theme remains page IndexedDB (`prefs.ts:1,55–67`), satisfying Q24.
