**Rulings (binding):**
- **R1 Recovery reset:** `dillad admin device revoke --all <user>` signs every device out and drops it from the device list. It is audited. Old encrypted history is lost unless another device holds it, and the command says so.
- **R2 Invite links:** stay one-time-visible. The README line becomes "by design: revoke and make a new one".
- **R3 Giphy:**
  - Search goes through the dilla server, so Giphy sees the server, not the person.
  - The picked GIF is downloaded by the server proxy and sent as a normal **encrypted attachment**. Readers never contact Giphy.
  - The key is the operator setting `giphy.api_key` in dilla.toml, off by default; without it there is no GIF button.
  - Show "Powered by GIPHY" in the picker.
- **R4 Bio and device names:** stored readable by the server, like display names. No avatar today.
- **R5 Process:**
  - One branch and one lane per item, with a written brief (no ad-hoc briefs).
  - Sonnet for recipe tasks, haiku for docs. Opus reviews auth, the proxy and the XSS surface.
  - Every gate includes `npm run lint`. e2e implementers get `DILLA_TESTKIT=/home/thim/.cache/dilla-w3/i37e2e-target/release/dilla-testkit`.
  - Local e2e runs one lane at a time, under `flock /home/thim/.cache/dilla-w3/e2e.lock`, to avoid the SFU port clashes seen today.

### E8 Giphy
- **Config:** `giphy.api_key` (and an optional `giphy.rating`, default `pg-13`) in internal/config. doctor reports whether it is on.
- **Routes:**
  - `GET /v1/gifs/search?q=&offset=` for members only. Rate-limited per user. It answers results with preview URLs that are rewritten to go through dilla.
  - `GET /v1/gifs/media/{id}?r=preview|full` fetches **only** from Giphy's media hosts (an allow-list; no user-supplied URL ever reaches the fetch, which closes SSRF). Size cap 25 MB, timeout, content-type check.
  - Both answer 404 when the key is unset.
- **Web:**
  - a GIF button in the composer opens a picker: search, a grid of previews through the proxy, and "Powered by GIPHY";
  - picking downloads the full GIF through the proxy, then sends it with the existing attachment path (packages/client-core/src/attachments), so it is encrypted like any file;
  - the button is hidden when the instance reports GIFs off (expose it in an existing config or features read).
- **Tests:**
  - server: the allow-list refuses other hosts, the size cap, 404 without a key, the rate limit, and Giphy faked with httptest;
  - web: the picker, send as attachment, hidden when off.
- Opus review focuses on SSRF, the DoS limits, key leakage (the key never reaches the client) and the privacy claims.
