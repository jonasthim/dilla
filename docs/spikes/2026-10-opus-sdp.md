# SP-09 Opus and SDP: caps hold with mono capture; mono processor output is required; real-call silence stayed at 50 packets/s

Date: 2026-10-04. Host: Linux dev box, Playwright 1.63.0, Chromium 153.0.8010.12, Firefox 155.0, LiveKit v1.13.7 in process, livekit-client 2.22.3 and the real `DillaE2EEManager`. The spec is `e2e/spikes/opus-sdp.spec.ts`; debug tokens connect the pages directly to the SFU.

## Question

Do the explicit microphone and screen-audio options give the 64,000/96,000 bit/s caps, Opus DTX/FEC and 20 ms packets assumed by DEV-08 and ruling F2? Does a `MediaStreamAudioDestinationNode` make microphone audio stereo? What sizes reach a sender transform during DTX silence?

## Microphone

The publish options under test were `{ audioPreset: { maxBitrate: 64_000, priority: "high" }, dtx: true, red: false, forceStereo: false }`. The initial capture deliberately disabled echo cancellation, noise suppression and automatic gain control to expose the source-channel dependency.

| check | Chromium | Firefox |
|---|---|---|
| remote answer Opus fmtp | `maxaveragebitrate=510000;minptime=10;stereo=1;usedtx=1;useinbandfec=1` | `maxplaybackrate=48000;stereo=0;useinbandfec=1;usedtx=1;maxaveragebitrate=64000` |
| source channel count | 2 | 1 |
| `usedtx=1` / `useinbandfec=1` | yes / yes | yes / yes |
| no `stereo=1` / no RED | no / yes | yes / yes |
| no `a=ptime` / `a=maxptime` present | yes / no | yes / no |
| `encodings[0].maxBitrate` | 64000 | 64000 |
| answer `maxaveragebitrate=64000` | no | yes |
| tone packets/s over 10 s | 50 | 50 |

Chromium failed the mono SDP criterion with this two-channel source: `forceStereo: false` alone did not remove `stereo=1`. Firefox reported a one-channel source and `stereo=0`. Both answers carried DTX and FEC, and neither contained `a=ptime`.

## Screen-share audio

`SCREEN_AUDIO` under test: `{ audioPreset: { maxBitrate: 96_000 }, forceStereo: true, dtx: false, red: false }`. Chromium used real headless display capture. Firefox headless has no `getDisplayMedia`; its result below uses an explicitly labeled synthetic `screen_share_audio` track.

Chromium subscriber decrypted 1152 frames during the publish leg. Its fake display audio track reported source `channelCount = 1`; the answer still set stereo because the explicit screen option requested it. Firefox synthetic track `getSettings().channelCount` was not exposed.

## Real-manager silence on the wire

A separate two-party LiveKit call published a microphone with `MIC_CAPTURE` and `MIC`, then attached a zero-gain/tone destination-node processor after publication. These are actual encrypted sender, RTP and subscriber deltas. Chromium changed payload bytes when the gain changed. Firefox payload bytes did not change, consistent with its suspended WebAudio source; its tone phase cannot establish an audible-tone rate.

| engine | phase | seconds | RTP packets/s | RTP bytes/s | encrypted frames/s | subscriber decrypts/s |
|---|---|---:|---:|---:|---:|---:|
| Chromium | silence | 20 | 50.00 | 959.60 | 50.00 | 50.05 |
| Chromium | tone | 10 | 50.30 | 9054.00 | 50.10 | 50.10 |
| Firefox | silence | 20 | 50.05 | 960.55 | 50.05 | 50.05 |
| Firefox | tone | 10 | 50.00 | 959.60 | 50.00 | 50.00 |

The loopback proves that the Chromium encoder can generate zero-byte frames and send fewer RTP packets under digital silence. The real-manager call still sent and encrypted about 50 packets/s in its zero-gain phase. This spike does not establish that dilla production calls obtain the loopback DTX packet saving. The worker encrypted and the subscriber decrypted every frame offered in the real-call phase.

Chromium’s source stayed two-channel with processing disabled even when the destination was mono; those rows retained `stereo=1`. With `MIC_CAPTURE` processing enabled, the source was one-channel and the answer was mono. The default destination still processed two channels, so the RNNoise destination must set `channelCount = 1` to keep the processed path mono. Destination mono alone is insufficient to repair a two-channel capture source. Some DTX flags varied between repeated rows in the same reused room; do not infer a stable per-row DTX effect from that matrix.

## Decision task 19 consumes

1. Keep `MIC = { source: Track.Source.Microphone, audioPreset: { maxBitrate: 64_000, priority: "high" }, dtx: true, red: false, forceStereo: false }`, paired with `MIC_CAPTURE = { echoCancellation: true, noiseSuppression: true, autoGainControl: true }`. Assert the captured source is mono where supported; the options alone did not make Chromium’s processing-off two-channel source mono.
2. Keep `SCREEN_AUDIO = { source: Track.Source.ScreenShareAudio, audioPreset: { maxBitrate: 96_000 }, forceStereo: true, dtx: false, red: false }`. Chromium real display capture met the stereo/DTX/RED/bitrate checks. Firefox synthetic publication also met its applicable checks, but real headless Firefox screen capture was not run here.
3. Set `DillaRnnoiseProcessor` destination `channelCount = 1`; task 19’s `MIC_CAPTURE` must be applied before publish. A mono destination is needed for the actual processed channel count and does not override a stereo capture source in LiveKit’s SDP decision.
4. Tone publication measured 50 packets/s in both engines, or 20 ms per packet. No `a=ptime` munging is indicated by these runs.
5. In 60 seconds of digital-zero loopback input, Chromium’s sender transform saw 2704 zero-byte and 143 1–2-byte frames. Firefox saw 2703 and 143 respectively while its AudioContext was suspended. The real manager call did not show loopback-like packet suppression in silence; task 22’s 400 ms DTX fixture must be described as a modeled load case, not a measurement of browser traffic.

## Limits and deviations

- The initial harness smoke timed out in this sandbox after browsers and the in-process SFU started; the isolated real-manager spike legs passed. A shorter `/tmp` symlink to the required worktree temp directory was needed because Chromium’s Unix socket path exceeded its limit under the long path.
- The Firefox tone phases were not audible because headless WebAudio stayed suspended. Firefox headless `getDisplayMedia` was not available; the synthetic screen publication is labeled above.
- No macOS, Windows, second LAN host, or Safari run was available here.
