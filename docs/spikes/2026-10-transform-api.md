## Question

livekit-client 2.22.3 forces `encodedInsertableStreams: true` on every PC when a custom E2EE manager exists
(RTCEngine.ts:794-809) and attaches receivers on Chromium with `createEncodedStreams`; PR #1703 disabled
`RTCRtpScriptTransform` on Chromium for an unexplained "InvalidState" error (facts-livekit-client R1). Does the
script-transform path survive transceiver reuse, a screen republish, `replaceTrack` and a signal reconnect
through real livekit-client and LiveKit, and on Firefox does any attach point other than
`EngineEvent.MediaTrackAdded` leak frames from a plaintext publisher?

Checked in the installed source (`node_modules/livekit-client/src`, 2.22.3):

- `Room.ts:997` passes `e2eeEnabled: !!this.e2eeManager`.
- `RTCEngine.ts:795-803` sets `rtcConfig.encodedInsertableStreams = true` whenever that is true and
  `createEncodedStreams` exists.
- `room/utils.ts:282-291` (`isScriptTransformSupportedForWorker`) returns false for every Chromium-based
  browser. Its comment reads: "Chrome occasionally throws an `InvalidState` error when using script
  transforms directly after introducing this API in 141."

## Criterion (ruling F8, DEV-28 (a))

Chromium stays on `createEncodedStreams` unless the script path passes **every** row below in all three runs:
all encrypted pairs decoding in every phase, `canaryRendered = 0`, `canaryDropped > 0`, `invalidState = 0`,
no pipe errors, and every `sendKeyFrameRequest()` resolving.

Expected (G3): the `TrackSubscribed` leg leaks frames on the initial-connect deferral; both `MediaTrackAdded`

not quoted below) leaked one frame at 43 ms twice and none once. Neither `MediaTrackAdded` leg presented
a frame or a loud window in any of the six runs.

## Notes on the measurements

- What the `InvalidStateError`s line up with (an inference from the counts; the rig does not record which
  pipe failed). The script path's pipe errors equal the streams path's retargets in every phase. A rig
  re-attach happens wherever livekit-client fires a second `MediaTrackAdded` on a receiver that is
  already attached:
  - steady: 6 on A;
  - each of C's five rejoins: 2 on A and 2 on B;
  - each screen republish that reuses a transceiver: 1 on B and 1 on C.
  That gives 6 + 20 + 4 = 30 in Chromium and 6 + 20 = 26 in Electron. On the streams path the rig posts
  `retarget` and keeps the streams it already transferred. On the script path it assigns a new
  `RTCRtpScriptTransform`, and the replaced transform's pipe errors with `InvalidStateError`. In this rig
  that did not stop decoding (12/12 everywhere), but it is the error PR #1703 cites, and the criterion
  counts it.
- Receiver reuse is routine through livekit-client and LiveKit: 30 re-deliveries of `MediaTrackAdded` on an
  attached receiver per Chromium run. Task 17's `DillaE2EEManager.attach` on the streams path must not call
  `createEncodedStreams()` a second time on such a receiver; it must re-point the worker. livekit-client's
  own `handleReceiver` does the same with `E2EE_FLAG`/`E2EE_TRACK_ID` and `updateCodec`
  (`e2ee/E2eeManager.ts:659-678`).
- `canaryRendered` stayed 0 on both paths and in both engines: `framesDecoded` plus `totalSamplesReceived` of
  D's tracks at every member. Chromium's `totalSamplesReceived` does not count concealment here while
  every audio frame is dropped before NetEq.
- No positive control exists for the Firefox audio observer: the rig never plays a plaintext audio path on
  Firefox. So "0 loud windows" means the WebAudio analyser heard nothing, and this spike has not shown it
  would have heard a leak. The video observer did see the `TrackSubscribed` leak.
- Firefox showed 6 `ontrack` receivers when the canary was already in the room (3 audio, 3 video) and 8 when
  it joined later, for a canary that publishes one microphone and one camera. Both `MediaTrackAdded` legs
  attached to every one of them (6 and 8 attaches). The `TrackSubscribed` leg attached only to the 2 that
  were subscribed.

## Decision task 17 consumes

1. Chromium attach API: `createEncodedStreams` (livekit-client's own path; DEV-28 (a) stands). Task 17's
   `DillaE2EEManager.attach` prefers the chosen API; the other stays implemented for the engines that need it.
2. Receiver attach point: `EngineEvent.MediaTrackAdded`, synchronously, on every engine; `TrackSubscribed` only
   maps metadata. Confirmed: in six Firefox runs a `MediaTrackAdded` attach presented 0 frames, while
   `TrackSubscribed` leaked a plaintext frame in three of the six.
3. The voice gate stays "(script transform or insertable streams) AND, on Chromium, the PC flag" (DEV-28).
