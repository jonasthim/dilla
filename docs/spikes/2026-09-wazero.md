Date: 2026-09-23. Decision owner: the W1 wazero card (spec risk 2, roadmap W1).

is a policy change, not a re-measurement.

Two of the three commit shapes land inside gap-18 §5.2's **middle band** for its
steady-state gate G2 (p99 ≤ 20 ms GO, > 60 ms NO-GO): Remove at 24.93 ms and
self-Update at 24.69 ms. gap-18 §5.2 is explicit that the middle "is not a silent
pass" — it is "go with a recorded caveat and a W6 re-measure card". R10 decides the
go/no-go and R10 is met with a 40× margin, so this is a **GO with that caveat
recorded**: G2's own numbers must be re-measured in W6/W12 before anyone tightens
the gate to gap-18's derivation. These two figures are `Process` + `Merge` only —
the 1,500-leaf base-state import happens before the timer starts — so they are
directly comparable with G2's definition; what differs is the host, which gap-18
never fixed.

Gate G1 of gap-18 §5.2 (the build gate) is met: `dilla-core-wasi` builds for
`wasm32-wasip1`, instantiates under wazero with `WithStartFunctions("_initialize")`,
and `internal/mlswasi/vectors_test.go` reports `Failed == 0` for all five suites.

**External Remove signing**, the second half of the W1 card ("wazero spike
(PublicGroup + external Remove signing) go/no-go", spec line 643; spec line 415
lists signing external proposals as one of the three jobs `dilla-core-wasi` exists
for): `TestExternalProposeRemoveSignsOnWasip1` signs an external Remove of leaf 0

Result: **PASS**, signing a 108-byte `MlsMessageOut`. The
go/no-go above is not GO unless this passed — a PublicGroup that cannot sign an
external Remove does not do what the card asked for.

`ExternalProposeAdd` and `ValidateKeyPackage` are **not** exercised on
wasm32-wasip1: both need a real `KeyPackage` and `testkit/fixtures/ds-1500/`
contains none (NV9). They are covered natively by Plan A task 11. If Plan A task 13
adds a `key_package.mls` to the fixture, add the matching smoke test and update

### If this is a NO-GO

gap-18 §5.3: the quadratic term is **per proposal**, so halving or quartering the
Add batch (256 → 64, a one-line `policy_version` change) cuts it 4× in a rare
operation. Try that before cbindgen and cgo, which costs `CGO_ENABLED=0` and a C
cross-toolchain per target. Record which lever was pulled:
not needed (GO) — no lever was pulled; the 256-Add worst case measured p50
85.234222 ms / p99 87.025789 ms, inside both R10's 1 s and gap-18 G3's 100 ms.

## What was measured, and how

- Commit latency is `Process` + `Merge` only. The base state is imported from
  `public_group_state.bin` before the timer starts, so the 1,500-leaf import is
  not counted. Every one of the ten fixture commits is valid at the same base
  epoch, so each is applied to a fresh 1,500-leaf tree.
- The DS does **no** HPKE and does not verify the membership tag:
  `PublicGroup::process_message` rejects `PrivateMessage` outright. The cost is
  Ed25519 verification, SHA-256 tree hashing and the O(n) credential-capability
  scan OpenMLS runs per queued proposal (openmls#2224). Spec risk 2's "HPKE cost"
  wording is wrong and should read "Ed25519 verification, SHA-256 tree hashing
  and O(n) credential-capability scans".
- Percentiles come from `TestGoNoGoCommitLatency`, 50 timed applications per
  shape. `go test -bench` reports a mean and cannot produce a percentile, so the
  benchmarks are for W12 comparability and the gate lives in the test.
- Resident memory is a whole-process `/proc/self/statm` delta across 8 instances,
  divided by 8, with the baseline taken **before** `New` so the per-instance linear
  memory and wazero state allocated at instantiation are inside the figure. It
  therefore also carries wazero's compiled-code pages, amortised over the eight
  instances; the `GATE rss_per_instance=` line splits the total into its
  instantiation and import halves so the two can be read apart. It is not an
  isolated per-instance figure; Go exposes none. The test runs alone, in its own
  process, because a whole-process delta is meaningless when `-shuffle=on` decides
  what ran before it. A negative delta is reported as a SKIP, never as a number.
- The gate tests are guarded by `DILLA_GATE=1` and are **skipped in CI**. R10's
  thresholds are defined on this dev box (16 cores, 30 GB); `ubuntu-latest` is a
  shared 4-vCPU / 16 GB runner and CI runs the package under `-race`, so the same
  code there is a different measurement. A red CI job is not a NO-GO, and a NO-GO
  is only ever declared from a `DILLA_GATE=1` run on the dev box.
- The host configuration is load-bearing and asserted by
  `TestClockAndRandomnessConfigurationIsLoadBearing`: with wazero's default
  1 ms-per-read fake clock every leaf's KeyPackage lifetime fails and
  `from_external` returns an error in microseconds. A wazero arm that looks
  impossibly fast is that bug, not a result.

## Re-running this in W12

Spec line 654 schedules the same 1,500-leaf DS test in W12, and line 635 says
numbers are published only from these runs. Run exactly:

```
DILLA_GATE=1 go test ./internal/mlswasi/ -run 'TestGoNoGoTreeImport|TestGoNoGoCommitLatency' -v -timeout 30m -count 1
DILLA_GATE=1 go test ./internal/mlswasi/ -run TestGoNoGoResidentMemory -v -timeout 30m -count 1
go test ./internal/mlswasi/ -run '^$' -bench . -benchmem -count 5 -timeout 60m
```

Without `DILLA_GATE=1` the three `TestGoNoGo*` functions skip, which is how CI
runs them. The RSS gate gets its own invocation on purpose (see above).

The benchmark functions are `BenchmarkPublicGroupFromExternal1500`,
`BenchmarkPublicGroupImportState1500`, `BenchmarkCommitApply1500` (ten
sub-benchmarks) and `BenchmarkCommitApply1500Interpreter`. Compare with
`benchstat`.

## Fixture expiry

`PublicGroup::from_external` validates every leaf's KeyPackage lifetime, and
`DEFAULT_KEY_PACKAGE_LIFETIME_SECONDS` is 84 days, so the committed fixture stops
working at `not_after` = 2026-12-23. `loadDS1500` fails with
`fixture expired, run dilla-testkit gen-public-group` rather than an opaque MLS
error. Regenerate with:

```
cargo run -p dilla-testkit --bin dilla-testkit -- gen-public-group --leaves 1500 --out testkit/fixtures/ds-1500/
```

Nothing schedules that regeneration; it is an open item (interfaces.md §7 item 3).

The compiler-versus-interpreter ratio in the table above is the median of the five
`-count 5` samples of each arm: 106 829 695 ns vs 12 680 467 242 ns for the 256-Add
commit (118.70×) and 45 908 435 ns vs 4 523 476 186 ns for the Remove (98.53×).
Both benchmark arms include the ~21 ms `PublicGroupImport` of the base state
(`BenchmarkPublicGroupImportState1500`, median 21 136 618 ns), which is why the
benchmark's 256-Add figure (≈107 ms/op) is larger than the gate's `Process` +
`Merge` p50 (85.2 ms): the gate excludes the import, the benchmark does not.
