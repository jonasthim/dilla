# LiveKit v1.13.7 in-process spike

Date: 2026-09-23. Host: dev box, linux/amd64, Go 1.27.0.
Pins: `github.com/livekit/livekit-server v1.13.7`,
`github.com/livekit/protocol v1.51.1-0.20260910121219-271d9cde3897`,
`github.com/livekit/server-sdk-go/v2 v2.18.2-0.20260922130803-2088dabd3442`
(see "Pins, and one that had to move" below), `github.com/pion/turn/v5 v5.0.13`
(not 5.1.x), plus LiveKit's three pion-fork `replace` directives copied verbatim.

## Result

LiveKit boots inside `dillad`'s process on 127.0.0.1:7880 and two Go-SDK
participants exchange a reliable data message over loopback.

| Measurement | Value |
|---|---|
| Startup, `sfu.Start` return | 102.362996 ms (`SPIKE startup=102.362996ms`; 102–153 ms across four runs) |
| First data packet delivered after | 1.060521859 s in the whole-suite run (`SPIKE data_delivered_after=1.060521859s`); 30.419929 ms when `TestTwoParticipantsExchangeADataMessage` runs alone. The publish loop retries every 250 ms until the data channel is open, so the high figure is four retries, not four seconds of latency. |
| Static binary, `CGO_ENABLED=0 go build -trimpath -ldflags=-s ./cmd/dillad` | 52,404,384 bytes (49.98 MiB) |
| Statically linked | yes — `ELF 64-bit LSB executable, x86-64 … statically linked … stripped` |

Reproduce by hand:

```
CGO_ENABLED=0 go build -trimpath -ldflags=-s -o dillad ./cmd/dillad
./dillad -sfu -api-secret <32+ characters>
```

## The four calls, in order

`config.NewConfig(yaml, true, nil, nil)` → `conf.ValidateKeys()` →
`conf.LoadTURNSecrets()` → `routing.NewLocalNode(conf)` →
`prometheus.Init(nodeID, nodeType)` → `service.InitializeServer(conf, node)` →
`go srv.Start()`.

- `NewConfig`'s third parameter is `*cli.Command` and its fourth `[]cli.Flag`;
  both take an untyped `nil`. With `c == nil` the whole CLI branch is skipped,
  `baseFlags` is never read, and no `cli.Command` is constructed.
  **dillad's own source never imports `urfave/cli`** — but the module is still an
  indirect requirement (`go mod tidy` records
  `github.com/urfave/cli/v3 v3.10.1 // indirect`), because
  `livekit-server/pkg/config` imports it, and it is compiled into and linked
  against every `dillad` build. The win is that no CLI flag parsing runs, not that
  the dependency is absent.
- `ValidateKeys` is the one call that refuses an under-specified config:
  `len(conf.Keys) == 0` returns `one of key-file or keys must be provided`.
  A short secret is only logged, so `Config.YAML` enforces the 32-character
  minimum itself.
- `LoadTURNSecrets` passes only because `rtc.turn_servers` is absent; the moment
  an entry exists it needs a secret or a username/credential pair.
- `NewLocalNode` returns `ErrIPNotSet` when `rtc.node_ip` is empty. With
  `node_ip: 127.0.0.1` and `use_external_ip: false`, `RTCConfig.Validate` skips
  `resolveNodeIP` entirely, so no STUN is attempted and `NodeIPAutoGenerated`
  stays false — which also keeps LiveKit's default public STUN list
  (`global.stun.twilio.com`, `stun.l.google.com`) out of the SFU's own
  PeerConnection.
- `prometheus.Init` must run before `InitializeServer`: it registers on the
  global default registry and the package's metric vectors are nil until it
  does. `internal/sfu/livekit_test.go` asserts the source order.
- `LivekitServer.Start()` blocks on `<-s.doneChan`, so it runs in a goroutine and
  `Stop(true)` closes that channel.
- `Stop` is a **no-op until the server is running**: it begins
  `if !s.running.Swap(false) { return }` (`server.go:373`), and the flag is only
  set at `server.go:333`, after a deliberate 100 ms sleep — while the TCP
  listeners were bound back at `server.go:246`. Aborting a boot inside that
  window (context cancelled, or the startup deadline expired) would stop nothing:
  the boot would finish, the goroutine would park on `<-doneChan` for good, and
  ports 7880/7882 would stay bound with no handle left to stop them. `sfu.Start`
  therefore never calls `Stop` directly on its error paths; `(*Server).abort`
  waits for `IsRunning()` — or for the boot goroutine to fail, which releases the
  listeners by itself — for up to 5 s first, and reports in the returned error if
  neither happened. `internal/sfu/livekit_test.go` covers both abort paths by
  asserting that the port accepts nothing afterwards.

## The setting that fails silently

`rtc.enable_loopback_candidate: true`. `CreateUDPMuxesFromPorts` starts from
`includeLoopback = false`; on a machine whose only interface is `lo` that yields
an empty address list, which is **not an error** — the server starts, signalling
works, and there are simply no UDP host candidates and no media. The same flag
also drives `SetIncludeLoopbackCandidate(true)` on the ICE setting engine. Both
are needed.

`tcp_port: 0` is safe here because `udp_port: 7882` is set: the network-type list
is non-empty, so the "TCP is forced but not configured" guard does not trip.

## Proxy paths dillad must forward

`/rtc`, `/rtc/validate`, `/rtc/v1`, `/rtc/v1/validate`.

## Metrics

LiveKit registers on Prometheus's **default** registry, so dillad's `/metrics`
must serve `prometheus.DefaultGatherer` (or `promhttp.Handler()`) for dilla's own
metrics and LiveKit's to appear together.

## Limits of this spike

- Loopback only. A browser on another host cannot complete ICE against this
  configuration; that is not what the spike claims.
- No TURN, no Redis, no egress or ingress, `development: false`.
- The Bot SDK's `server-sdk-go/v2/pkg/media` is **not** imported anywhere and
  must not be: it pulls `github.com/livekit/media-sdk/opus`, a single file with
  `#cgo pkg-config: opus` and no build-tag fallback, which would cost
  `CGO_ENABLED=0` and require libopus headers on every architecture.
  `TestNothingInTheModuleImportsTheCgoMediaPackage` asserts it over the **whole
  module's** transitive import set (`go list -deps -test ./...`), not just over
  `internal/sfu`'s own files. `-test` is part of the assertion, not a
  convenience: the SDK is imported only from test files, so the plain
  `go list -deps ./...` walks a graph that contains neither the SDK nor
  `pkg/media`, and the check would pass without proving anything.

## Pins, and one that had to move

`server-sdk-go/v2` is pinned to `v2.18.2-0.20260922130803-2088dabd3442`, the
module's `main` head at 2026-09-22, not to the newest release tag `v2.18.1`
(deviation B13). v2.18.1 requires `livekit/protocol v1.49.0`; `livekit-server
v1.13.7` requires the `v1.51.1-0.20260905…` pseudo-version; MVS lifts protocol to
v1.51.1, and `server-sdk-go`'s `sipclient.go:354` then returns
`*livekit.TransferSIPParticipantResponse` where its own signature declares
`*emptypb.Empty`, so the package does not compile. Pinning protocol back to
v1.49.0 with a `replace` fails the other way: `livekit-server v1.13.7` imports
`github.com/livekit/protocol/datatrack`, which v1.49.0 does not contain. The
pseudo-version above is the combination verified to build on this box on
2026-09-23. It is an unreleased commit pinned by hash: when a `v2.18.2` or later
tag appears whose protocol requirement is compatible with `livekit-server
v1.13.7`, move to it and delete this paragraph.
