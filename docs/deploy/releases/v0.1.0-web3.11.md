# dilla v0.1.0-web3.11

Released 2026-10-21.

AFK now means disconnected. Until now, an idle desktop was moved into a listen-only call in the AFK channel, which kept a media room open for people who were not there. From this release the AFK channel never hosts a call: the people in it are listed as **away**, with no voice connection at all. The release also changes the installer so that `install.sh --upgrade` refuses to restart the media server while a call is live.

## What's new

- **No AFK call.** Nobody joins a call in the AFK channel, and it opens no media (LiveKit) room. An idle desktop no longer keeps a room open, so the load on the media server drops and an empty server really is empty.
- **The away list.** The AFK row lists everyone who is away in that server, each with the word "away" after the name, and counts them ("2 in AFK"). It is kept up to date live.
- **The AFK page.** Opening the AFK channel shows the same list, or "Nobody is away.", and a **go AFK** button. Once you are away, the button is replaced by "You’re away. Join a voice channel, send a message or type to come back."
- **Go AFK yourself.** Click the AFK row, or press **go AFK** on its page. You leave any call you are in (on this device and on your others) and are listed as away.
- **"Moved to AFK" for the sweep.** After the inactive timeout, a computer idle in a call is disconnected, listed as away, and its screen says "Moved to AFK for inactivity" with the AFK channel's name. Nothing joins, and no microphone is asked for.
- **"You went AFK on another device."** When you choose AFK on one device, your other devices' calls end with this calm notice, not a "removed" error.
- **What brings you back.** Away ends when you join a voice channel on any device, when you send a message or start typing in that server, or when your last connection closes. There is no "leave AFK" action.
- **A phone is still never disconnected** for being idle.
- **Wording.** The settings no longer say people in AFK are "muted": the inactive-timeout hint now says members "are disconnected and listed as away", and the AFK channel's edit dialog says "Nobody is connected here; people who are away are listed."
- **Installer: refuses to restart live calls.** `install.sh --upgrade` now runs `dillad media --rooms` as the service user, with the installed config, at the moment it is about to stop anything. If a room has participants it prints the rooms and their participant counts and exits with an error, having changed nothing. If the check itself fails, it refuses too. `--yes` upgrades anyway, with a warning. An instance still running the old all-in-one SFU (`livekit.mode = 'in_process'`) cannot be asked, so its first upgrade also needs `--yes`: that upgrade ends every live call.

## Versions

| | web3.11 | Upgrade and rollback |
|---|---|---|
| Server schema | **21** (was 20) | Migration 00021 `community_afk_away`. **Rollback needs `migrate down`, see below.** |
| Client store | **5, unchanged** | Safe. |
| Wire | **2, unchanged** | Safe. Op 55 (`afk_away`) and a fifth element of the AFK snapshot are additive; older clients ignore them. |
| Browser and WASI ABI | **unchanged** | Safe. The cores are unchanged. |

## Operator notes

- **Schema 21.** Migration 00021 adds one table, `community_afk_away`: one row per member who is away in a server. The server also gains one route, `PUT /v1/communities/{id}/afk/away`. Nothing else is stored.
- **Rollback is not the usual `dillad.prev` swap.** The database is at schema 21 after the first start, and web3.10 refuses to start on a database newer than its own migrations. Putting the old binary back as it is leaves it refusing. Take the database down first, **with the new binary** (only it knows the way down), and then reinstall web3.10:

  ```sh
  systemctl stop dilla
  runuser -u dillad -- /usr/local/bin/dillad migrate down --to=20 --i-know-what-i-am-doing --config=/etc/dilla/dilla.toml
  # then put web3.10 back: install.sh --upgrade --version v0.1.0-web3.10 (or restore dillad.prev by hand)
  systemctl start dilla
  ```

  The down step drops `community_afk_away`; web3.9 and web3.10 would ignore the table anyway. The only thing lost is the away list, which refills as people go AFK. If the new binary fails to start during `install.sh --upgrade`, the installer already runs this step itself before it puts the old binary back.
- **At the first start, live AFK calls end.** Any call still running in an AFK channel (web3.9 and web3.10 kept them) is ended, and the people in it are listed as away. A person who has no connection is dropped from the list again about a minute after the start.
- **The AFK channel never opens a LiveKit room.** A start there and a media token for it are refused (`403`). A server where everyone is idle now has no rooms.
- **Check for live calls immediately before the restart.** Restarting `dillad` restarts the media server (SFU), which disconnects every live call. The installer now does this check itself, right before it stops the service, and refuses while a room has participants (`--yes` overrides). To check by hand, run `dillad media --rooms --config=/etc/dilla/dilla.toml`; it prints `no live rooms`, or each room with its participant count. The answer goes stale: one taken ten minutes earlier proves nothing.
- **Corroborating with the journal.** Every attached device posts to `calls/{id}/stats` every 10 s, so no such posts in the last 2 minutes means no attached device. Do not trust a zero until the grep pattern has been checked against a window that is known to contain a call: run it over a minute in which you were in a call yourself, and see that it finds your posts. A pattern that silently matches nothing looks the same as an empty server.
- **The internal health probe uses the `plain_listen` address.** `dillad` binds only `server.plain_listen`, not the loopback address, so `curl http://127.0.0.1:8080/healthz` returns `000` unless `plain_listen` is exactly that. Use the address in `server.plain_listen`, for example `curl -fsS http://10.0.0.5:8080/healthz`.
- **The new browser client comes inside the `dillad` binary.** Open tabs pick up the new build and reload.

## Known limits

- **Old tabs.** A web3.9 or web3.10 tab that is still open ignores op 55 and the away list. Its AFK snapshot also fails to decode (an AFK decode error) for a device cut by a chosen AFK (`pending` = 2) until the tab reloads. The new build reloads open tabs, so this is brief. The person sees "You were removed from voice." instead of the calm line, and the tab keeps retrying the AFK read; if it then goes offline before its next join, every community voice join fails until it reloads. In short: a tab from before web3.11 may be unable to join community voice until it reloads. Reload any tab that was open across the upgrade; the new build normally reloads open tabs on its own. Until it reloads, pressing AFK in such a tab gets a `403` join failure.
- **The away list holds the first 1024** people of a server. A server with more away at once lists only those.
- **A brief disconnect can drop someone off the list.** When a person's only connection closes, they are cleared at once. If it was a network blip, they are listed again only at the next sweep, or when they next go AFK.
- **A person removed from a server** (a kick or leave at the same instant as an admission or a disconnect) may still be shown as away to the others until they next read the list.
- **One `dillad` process per database.** The away index lives in memory. A backup restored under a running instance is cleared only after the next restart.
- **Messages in direct messages do not bring you back.** A message or typing in a server's text channel does; one in a direct message does not.
- **Away notices are not queued across a restart.** Every client reads the list afresh when it reconnects, so nothing is lost, but a notice not yet sent at shutdown is dropped.
- **Timing at the first start.** Marking after a restart does not check who is still connected; the sweep a minute after the start corrects it.
- **The AFK page is a list, not a stage.** It shows the away people and the **go AFK** button, with no tiles.
- **Deciding whether another of your devices is in a call** lists the media server's rooms once per cut device. This is fine at self-hosted scale.
- The web3.10 known limits still hold.
