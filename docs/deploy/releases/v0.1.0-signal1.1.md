# dilla v0.1.0-signal1.1

A fix release on top of [v0.1.0-signal1](v0.1.0-signal1.md): PR #123 (Bot installer) and PR #128 (Bot and web client
fixes). The release includes `dillad` (with the web client), `dillabot`, their matching core modules, installers and
checksums.

## What's fixed

- **/poll and /remind work again on servers with Music on.** A Bot with Music on reports the music announcement
  operation (25) among its capabilities. The web client only knew operations up to 24, so it rejected the whole report,
  and slash commands, poll votes and closing a poll did nothing in those servers. The client now accepts 25 and ignores
  any operation it does not know instead of rejecting the report (an unknown operation grants nothing). CI now fails when
  the Bot gains an operation the web client does not list.
- **The Bot no longer stalls behind one failing event.** A group event that keeps failing no longer blocks every event
  after it:
  - Events for a group that is gone, and reads the server definitively refuses, are skipped and logged.
  - An event still failing after an hour (24 hours for text-channel messages, so moderation has time) is acknowledged.
    This needs at least three failed passes, and changing the clock does not shorten it.
  - When one sender's trust is stale, only that person's commands are held, and the hold fails closed. A held event is
    dropped after an hour of consecutive held passes.
- **The Bot answers sooner.** The interaction fast path refreshes trust before it reads, polls at most four groups at a
  time, and is charged per group within one budget per installation.
- **Admitting a Bot interaction no longer queues every other write.** The receipt cleanup searched every receipt kept in
  the 30-day window. On a busy instance that took about 6 s per admission, with the server's other writes waiting behind
  it. New indexes serve it, and each admission deletes at most 512 expired receipts.
- **The web client:**
  - The provider status gives each answer its own deadline.
  - The message log stays at the end when a row grows, and pressing a message does not scroll it.
- **`dillabot doctor`** checks the service's `PATH` and reads `/etc/dillabot/bot.toml` (#124).
- **`install-bot.sh --upgrade` prunes its pre-upgrade copies.** It keeps the 3 newest copies under `/var/backups/dillabot`
  after a successful upgrade, never the copy it just made. `--keep-backups N` changes the number. This is the first
  release whose installer prunes (signal1's did not, see its notes).

## Database migrations

| Migration | What it does |
|---|---|
| `00053_bot_interaction_admission_expiry` | Adds two indexes on `bot_interaction_admission_receipts` (installation, expiry; one partial, for receipts that still hold a payload). It changes neither what is kept nor for how long. On an instance with a large receipt backlog the index build takes a moment at startup. Its down migration drops both indexes. |

## Deploy order

1. Back up the server database and config. Check that no call is live (`dillad media --rooms
   --config=/etc/dilla/dilla.toml`), because the upgrade restarts media and ends calls.
2. **Upgrade `dillad` first** with `install.sh --upgrade`. Confirm `dillad migrate status` shows 53, the service is
   healthy, and a browser signs in.
3. **Ask everyone to reload their open tabs.** Until they do, a tab keeps the old client, and /poll and /remind stay
   broken in servers with Music on. Open tabs also find the new build by themselves.
4. **Then upgrade `dillabot`** with `install-bot.sh --upgrade`. On a host that collected many pre-upgrade copies under
   signal1, this upgrade prunes them down to the 3 newest.

Rolling `dillad` back to signal1 is possible. Wire and the browser store are unchanged, and `migrate down --to=52` only
drops the indexes. The "No rollback below wire 4" rules in signal1's notes still apply.

## Known limits

- The commit watchdog can remove a channel's only member when they take more than about 6 s to commit (for example,
  while creating several channels right after installing the Bot). Nobody is then left who can commit, and others stay
  on "joining this channel…". A fix is in review for the next release. Deleting and recreating the channel works around
  it. No such channel has been seen on the Homelab instance.
- Closing a call group leaves its pending Remove proposal in the database, never voided. This only grows a table and
  affects no one; the next release voids them and cleans up the backlog by itself.
