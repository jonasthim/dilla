# dilla v0.1.0-web3.13

Release date: set when the release is published.

Calls survive an upgrade. `install.sh --upgrade` now restarts only the API when the running media server (SFU) can stay, so people in a call keep talking while `dillad` restarts. An open tab that picks up the new build mid-call reloads and rejoins by itself, with audio back within a couple of seconds of the reload. TURN moves out of the API process, so a relayed call survives an API restart too.

> **A rollback to web3.12.x is not the usual `dillad.prev` swap, and it ends calls.** The database moves to schema 24 at the first start, `systemctl stop dilla` no longer stops `dilla-media`, and the old `dillad` cannot share `turn.listen` with a media server that holds it. Follow [Rolling back](#rolling-back-to-web312x) in the operator notes.

## Why this release exists

Before this release, an upgrade that restarted `dilla-media` ended every live call, and a client that had to rejoin did so through an orderly self-Remove. That self-Remove turned a short blip into a lost call. It is the reason two of three people did not come back after the web3.11 upgrade. The call was gone from their side as soon as the blip started, so nothing was left to rejoin.

## What's new

### Exercised by tests

All of this ran in the browser suite (`e2e/voice/upgrade.spec.ts`, `update-resume.spec.ts`, `reload.spec.ts`), in Go and Rust tests, or in `deploy/install_test.sh`, as listed under "Numbers". What has not run outside tests is under "Not yet seen working on a real instance".

- **`install.sh --upgrade` restarts only the API when the media server can stay.** The installer reads the running media server's media level and compares it with the new release's `min_sfu_media_level` from `release.json`. Level 2 is this release's media server; `min_sfu_media_level` is 1. A web3.11 or any web3.12.x media server counts as level 1 (it is identified by its executable, `dillad` or `dillad.prev`, never by what it says about itself), so an upgrade from any of them to web3.13 is `when-idle`: only `dilla` restarts, live calls continue, and there is no live-call refusal and no `--yes`. The installer logs its decision and why ("decision: keep dilla-media running: …", "decision: restart dilla-media, which ends any live call: …"). A media server whose executable the installer cannot identify gets a restart, which ends its calls: that covers one two or more releases back (its executable matches neither the installed `dillad`, `dillad.prev` nor the pinned web3.11 binaries) and a self-built binary.
- **`dilla-media-refresh.timer` moves the media server onto the new binary when its calls end.** It runs every minute as root (`dilla-media-refresh.service`, `/usr/local/libexec/dilla-media-refresh`). It restarts `dilla-media` only when its executable differs from `/usr/local/bin/dillad` and `dillad media --idle` exits 0: no room has participants, none is younger than 60 s, and the API reports no call token minted in the last 60 s. Anything else, including an API that does not answer, means not now. Every restart is logged to the journal, and a quiet minute logs nothing. The installer enables the timer.
- **`dilla-media.service` changed.** It drops `PartOf=dilla.service`, so restarting or stopping `dilla` no longer touches it. It is `Type=notify` (`NotifyAccess=main`, `TimeoutStartSec=60s`): `dillad media` sends `READY=1` once the SFU accepts RoomService requests and `media.json` is written, so `systemctl start dilla-media` returns when the media server is ready. It gains `NoExecPaths=/` and `ExecPaths=/usr/local/bin`: **`dillad` must be the statically linked release build** (`CGO_ENABLED=0`). A dynamically linked self-build cannot start under this unit. It gains `AmbientCapabilities=CAP_NET_BIND_SERVICE` only when `turn.listen` is below port 1024 and TURN is on.
- **Install flags.** `--restart-sfu` restarts the media server now and ends live calls. `--yes` is still accepted for this release, only to let a restart that the release needs end live calls (and for the `in_process` migration); it never forces a restart, so a script that always passes `--yes` keeps its calls on a compatible release. The installer says "--yes goes away in the next release". `--release-json FILE` goes with `--binary` and is checked against `--sums` and the binary.
- **TURN runs in `dilla-media`.**
  - Behind a proxy (`tls.mode = "behind_proxy"`): the same `turn.listen`, `turn.proxy_protocol`, `turn.relay_ip` and `turn.public_url`, read by the media process at the same address. Nothing to edit.
  - Public mode (`acme_tls_alpn`, `acme_dns`, `acme_ip`) **without `turn.listen`**: nothing changes. TURN stays on 443 behind the TLS demultiplexer, in the API process. **A relayed call does not survive an API restart there**, see the next point and "Known limits".
  - Public mode **with `turn.listen`** (new, opt-in; it needs `livekit.mode = "sidecar"`): `dilla-media` serves `turns:` on that port, with the ACME certificate read from the shared storage (it never issues or renews), and the instance hands clients `turns:<host>:<port>?transport=tcp`. The API binds no 443 relay then. It costs a port to open.
  - **The handoff from a web3.11 or web3.12.x media server happens once**, at the first idle refresh after the upgrade. `dilla-media` restarts, `dilla` is restarted so it lets go of `turn.listen`, and `media.json` then lists `turn`. The rooms are empty, so no relay is in use. Exactly one process holds `turn.listen` at a time.
  - Credentials are unchanged (`turn.shared_secret_file`, no new secret). The media relay refuses every credential issued before its own start.
  - Two sockets in the state directory (`instance.data_dir`, `/var/lib/dillad` with the shipped units), mode 0600 and checked against the `dillad` uid: `media.sock` (served by `dillad media`) and `api.sock` (served by `dillad serve`). Relay cuts and the barred-device lookup go over them. `media.json` (`version`, `media_level`, `capabilities`, `pid`, `started`) is the media server's description of itself; it lists `turn` only after `turn.listen` is bound. While `dilla-media` serves TURN, `api.sock` is required: `dillad serve` exits 69 when it cannot bind it.
  - A device cut from the relay gets `503 E_UNAVAILABLE` (retry after 2 s) from a call start until `dilla-media` has acknowledged the cut.
- **Relayed calls survive an API restart.** In public mode, TURN on 443 runs in the API process, and every API restart used to drop relayed callers for good: the restarted relay refuses every credential issued before its start, the page reconnected with its old credentials, and about 30 s later the room sweep removed it. They were shown "You were removed from voice." and had no rejoin. The new route `POST /v1/calls/{call_id}/relay` (body `[]`, answer `200 [ice_servers]`) mints fresh relay credentials and does nothing else: no room, no token, no SFU call. It applies the call start's gates (`view_channel`, `connect`, a current leaf, not barred, no pending repair or relay cut). The page asks it for fresh credentials on every reconnect, once per reconnecting episode, retrying after 1, 2 and 4 s and then every 5 s, and stops asking within that reconnect after a 403, a 404 or `E_NO_CALL`. If the removal still arrives while the page is reconnecting, the page treats it as a lost connection and rejoins, unless the channel is really gone for this device.
- **A tab that reloads into the new build rejoins by itself.** Before it reloads, a tab in a call holds the call group instead of leaving it. The next join of that channel resumes it (catch up, commit a fresh epoch, then publish), or, when a peer has already committed its departure, rejoins by a fresh join within the same budget. In a real upgrade pages pick up the new build up to 3 s apart, so a page that a peer left behind often comes back the second way. Two windows apply. The page's rejoin window counts only the time the instance answers, not wall-clock time, so the page keeps trying through an outage. The hold itself (the fast resume) lasts 180 s of wall-clock time: after a longer outage the hold is released when the instance first answers, and the call comes back by a fresh join. An update reload that lands while such a resume is still starting keeps the hold too. No microphone click is needed in Chromium; Firefox can ask again, see "Known limits".
- **A resume commits a fresh epoch before it publishes (UP6c).** A held call used to hand the new page the held epoch, and the new page's sender then restarted its frame counter at 0 under the same key. Now the resume runs `call_rotate` (an UpdatePath of its own leaf) after the start and before any media key reaches the page, so SFrame nonces are never reused. Every resume moves the epoch by one per resumer.
- **Everyone dropping at once is covered.** An absence Remove is **withdrawn** when the departed device itself resumes, and only that device's own (Jonas: "Only its own"). A new handshake kind 3 (`withdrawn`) tells clients, and a commit that applies a withdrawn proposal gets `409`, detail `withdrawn`. The first device back keeps its place; the others rejoin the same call, usually by a fresh join, up to about 30 s after the server answers. This is deliberate: a device that really left keeps its key material no longer than the normal sweep window. Kind 3 is sent only to clients that ask for it (`identify` caps bit 0, `kinds=3`); a tab from before web3.13 never sees it and, until it reloads, its commits in such a group get `409`.
- **A pending cut or an unreachable SFU is transient.** A call start and the `/rtc` gate answer `503 E_UNAVAILABLE` with `retry_after_ms` 2000 and the detail "your device's access to this call is being settled" for a pending repair or relay cut (a pending repair was `403` before), "your device's place in this call is being settled" for a withdrawal that could not be decided, and "the media server is not answering" when `CreateRoom` or the token mint fails (this was `500 E_INTERNAL`). Nothing is minted or admitted, and once the repair lands a barred device still gets its 403. Clients retry.
- **Only a call that ended as it was opened sends the client back to the start.** The call start's `503 E_UNAVAILABLE` for a call that ended as it was opened (a start racing the idle close of its call group) now carries a fourth element in its error body, reason `call_ended` (the detail text is unchanged; clients never read details). It is the only start 503 after which the client forgets the call group and reads the call again. On every other start 503 (the three above, and a call that is busy) the client keeps its place: a fresh join whose start is refused holds the group it just joined, and the next join resumes it with no second external commit. Before, a page that joined while the media server was restarting forgot its leaf, joined again and left again (three epochs an attempt), and a device whose access was being settled read "rejoining" for up to 30 s. Operators see the change only as that element in an error body. A tab from before web3.13 ignores it and still forgets the group on any start 503 until it reloads, as before; that costs epochs, never correctness. A web3.13 page talking to an API rolled back to web3.12.x reads that API's ended 503 as transient: it holds the group, and its next join, whose call read no longer names the closed group, joins the new one.
- **After an outage the first device is back in about a second.** The gateway now probes the instance (one plain `GET /v1/instance`, 1.5 s timeout) every 1.5 s plus up to 0.5 s of jitter while its reconnect backoff is long, so the first device is back about 1 to 2 s after the API answers. It used to wait for the backoff, about 8 s. After 5 minutes of continuous probing the interval grows to a cap of 10 s, so an outage longer than 5 minutes is noticed within about 10 s.
- **A proxy's 401 is not a sign-out.** A 401 without the `X-Dilla-Generation` header that the instance stamps on its answers counts as an unreachable instance (the client probes), not as signed out, and it is not retried as a reauthentication. A 503 or 429 without the header is also not trusted for its `Retry-After`.
- **Commands.** `dillad version --json` prints one line: `version`, `revision`, `wire` (`[2]`), `schema` (24), `media_level` (2), `min_sfu_media_level` (1) and `media_capabilities` (`["turn"]`). `dillad media --idle` exits 0 when idle, 1 when busy (the busy rooms go to stderr) and 69 when it cannot tell. `dillad media --self` prints the running media server's self-report from `media.sock`, as one JSON line.
- **`dillad doctor` legs.**
  - `turn` names who serves the relay ("served by dilla-media" or "served by the API (dilla)"), asked of both sockets; it is red when both or neither serve, and red when `dilla-media` serves TURN but `api.sock` does not answer (run doctor as `dillad`, it serves only that uid). It adds "N cuts not yet acknowledged by dilla-media" in yellow. In the public-mode opt-in it probes `turn.listen` over TLS. The installer's summary counts those three ownership reds as a problem with the install itself ("doctor found a problem with the install itself: turn", a non-zero exit), not under "these checks need DNS, the network or the proxy set up first"; a failed `turn` probe still counts as pending.
  - `media_binary` is green when `dilla-media` runs this binary's version, yellow while it runs another ("dilla-media runs vX, an older media level (…) than this binary's (…); it restarts onto this binary when its calls end (dilla-media-refresh.timer)"; for a web3.11 or web3.12.x media server, which writes no `media.json`, it reads "dilla-media's build is unknown (…); it restarts onto this binary when its calls end"), red when its media level is below the oldest this API works with, and "skipped" when the SFU is not a sidecar.
  - `media_refresh` is yellow while `dilla-media` waits to become idle on an older binary, and red after 24 hours. The restart is then the operator's call: `dillad media --rooms`, then `systemctl restart dilla-media`.
- **Config validation.** `turn.listen` outside `behind_proxy` is now accepted, and only with `livekit.mode = "sidecar"`. `turn.proxy_protocol` outside `behind_proxy` is now refused ("turn.proxy_protocol is only read in behind_proxy mode"). web3.11 and every web3.12.x refuse `turn.listen` in every `tls.mode` but `behind_proxy`.
- **The release has a `release.json` asset and a compatibility gate.** The release assets are now `dillad-linux-amd64`, `dillad-linux-arm64`, `dilla_core_wasi.wasm`, `install.sh` and `release.json`, all five listed in `SHA256SUMS` (which is the sixth file). `release.json` is generated by `release.yml` from the built binary's `dillad version --json` and the previous release; it states `format`, `tag`, `version`, `wire`, `schema`, `media_level`, `min_sfu_media_level`, `media_capabilities` and `sfu_restart` (`when-idle` or `required`). The installer refuses a `release.json` that does not match `SHA256SUMS` or the binary, and refuses a release from web3.13 on that lacks one. A new CI job, `sfu-compat`, runs `upgrade.spec.ts --grep compat` against the previous release's real binary as the media server, and `release.yml` will not publish unless that job passed on the commit. A second new job, `upgrade-e2e`, runs the full `upgrade.spec.ts` (B1, B2, A2 and A) on Chromium and Firefox, on every push to main and by hand (`workflow_dispatch`). It is not required: `ci-ok` does not need it, so an upgrade regression shows after the merge, not on the pull request, and a release still needs its quiet-machine run. The full spec runs only with `DILLA_E2E_UPGRADE=1`, so the voice suites of `chromium-web` and `firefox-web` skip it. The media level itself is pinned by a guard test (`internal/sfu`, `TestMediaLevelGuard`), so a change to the API-to-SFU contract without a bump fails CI.
- **Copy.** No new UI string. The messages people may see in a call are the existing ones: "reconnecting" in the call panel, "You were removed from voice.", "You left the call while away." and "The connection to voice was lost. Join again to continue."

### Numbers

All timings are Chromium on one development machine, with the test host and a separate `dillad media`, unless a browser is named. They come from the development logs of each part (compat job, resume, outage probe, acceptance spec, relay route, requeue fix).

- **Compat against the real web3.12.3 media server** (`upgrade.spec.ts --grep compat`, `DILLA_SFU_BIN` set to the release's `dillad-linux-amd64`): 3 of 3 passed after the relay route (37.9 to 42.0 s each), and again once after the last client change (41.1 s). Carol, forced to a relay, is heard again 18.65 to 21.0 s after the API-only restart, with no leave reasons. Before the relay route the same job failed 3 of 3: carol was removed and never rejoined.
- **`upgrade.spec.ts` on Chromium:** 5 of 5 and then 3 of 3 after the last core fix (UP13), 8.7 to 14.5 minutes a batch. The earlier flake, a resume commit that lost a 409 race and fell back to a second start, is fixed in the core and no longer seen: the race still fires, and each time the page caught up and committed again with one start.
  - API-only restart, same build (B1): the same LiveKit participants, no `removed` phase, no new epoch, and the largest inbound frame gap per pair was 400 to 850 ms. The API was down 5.1 to 7.2 s.
  - New build, every page reloads (B2): each page was published again 0.6 to 2.1 s after pagehide, and each peer heard it again within 3.8 s at most (the check is 5 s). In the logged runs all three resumed with no external join, but B2 does not assert that: its three pages reload together, and the 5 s budget covers a resume and a fresh join alike.
  - Everyone dropped at once and nobody left to commit (A2): the first device back resumed 0.4 to 0.55 s after it started joining, and was back **0.56 to 1.6 s after the API answered** (before the gateway probe it was about 8.1 s). Three withdrawable Removes were in the database, one kind-3 row per resumer afterwards, the same group, and a rotation commit after all three were back.
  - Full restart with a new media server (A): all three reloaded, connected and hearing each other 4.9 to 9.0 s after the answer.
- **Firefox:** `update-resume.spec.ts` passed (the resume was published 1.03 to 1.28 s after pagehide, a real resume with no external join). `upgrade.spec.ts` on Firefox was last run for UP9: B1 and B2 passed in the runs that finished (largest gap 404 to 852 ms in all but one run, B2 published 0.95 to 1.09 s after pagehide), A2 did not pass reliably (see below).
- **Unit and integration:** client-core 2244 and web 2522 vitest tests, `cargo test -p dilla-core -p dilla-testkit`, `deploy/install_test.sh` 137 checks (the keep and restart decisions, the web3.12.3 media server kept while calls are live, an unknown executable restarted, the web3.12.x rollback stopping `dilla-media` first and refusing a public-mode `turn.listen`, a failed rollback to web3.12.3 enabling the refresh timer again, and the three TURN ownership reds failing the install), and `check:docs`, `check:copy`, `check:ci`.
- **A rollback of the migration** is tested for SQLite (`cmd/dillad/migration_00024_test.go`, `TestDown00024ThenOldBinary`): down to 23 drops the kind-3 rows and the withdrawn proposals, and the previous binary's `migrate status` then reads the database. The old binary does not serve and fetch handshakes in that test.
- **By hand, once, not in CI:** the old-core check. The previous release's core (built from a checkout of the v0.1.0-web3.12 tree) refuses a handshake page that carries a kind-3 row with `E_CORE_INPUT`, and applies the same page with that row left out, carrying the sequence gap. This is why the server sends kind 3 only to a client that asks for it, and why the rollback deletes those rows.

### Not yet seen working on a real instance

- **A real public-mode relay restart.** The relay in the API process, restarted with the API, is covered only by the compat job (the web3.12.3 media server runs it in the API's place); no test host in public mode with the 443 demultiplexer exists.
- **A quiet-machine run.** The e2e batches ran on a loaded development machine (load average 4 to 24), and the final numbers above come from runs at lower load. A run on a quiet machine is pending; the controller fills it in at release.
- **Firefox `upgrade.spec.ts`, A2 (everyone dropped at once).** It failed intermittently in UP9 (2 of 5, then 1 of 3 twice), with one peer never reconnecting within 90 s of the answer in some runs. The cause was not fully pinned (the acceptance-spec notes); it has not been run on Firefox since the later fixes. A2 on Firefox is flaky and unexplained. A Firefox listener also dropped a relayed peer's frames after a reload in some UP9 runs (`bufferTimeout`), which is in the receive pipeline and not diagnosed here.
- **The Firefox microphone prompt after an update reload.** Where the browser asks every time, the new page may ask again before it publishes; the resume budget does not cover the wait for a click.
- **A rollback from schema 24 and from a running web3.13 media server on a live instance, and the TURN handoff on a real public-mode install.** The migration down and the installer paths are tested; nobody has done them on a deployed instance.
- **Postgres.** Migration 00024 has a Postgres file; the store tests ran against Postgres in a container on a fresh database, and no upgrade of an existing Postgres instance has been watched.

## Operator notes

- **What web3.12.2 to web3.12.4 already shipped, where it meets this release.** Those are patches on main, with no migration (schema 23 throughout) and no media-level change. web3.12.3 gave the core `E_DEVICE_REVOKED`, so web3.12.4's core hash is the baseline `HASH_FULL` replaces. #83 (web3.12.4) retries a call join once when another member commits between its two reads; UP13's requeue fixes a different path, a refused resume commit, and the two do not overlap. #82 (web3.12.4) re-subscribes in Firefox when audio is filed under a spare slot after a rejoin ("E_MEDIA_MISROUTE" in Settings → Diagnostics); UP9 saw a Firefox listener drop a relayed peer's frames after a reload, which may be the same cause, but `upgrade.spec.ts` has not run on Firefox since #82 and it is not claimed fixed. The compat job's baseline media server is web3.12.3's real binary.

- **Schema 24.** Migration 00024 adds three columns to `mls_pending_proposals` (`withdrawable`, `withdrawn_at`, `withdrawn_seq`, all empty for existing rows) and rebuilds `mls_handshakes` so its `kind` check allows 3. Nothing is rewritten besides copying `mls_handshakes` rows. **SQLite takes another `<db.path>.pre-migration-<unix time>` copy at the first start**, so the count of those copies beside the database grows by one at this upgrade (dillad deletes none of them; remove old ones yourself).
- **Nothing new is required in `dilla.toml`.** Behind a proxy, nothing changes. Public mode keeps TURN on 443 unless you set the optional `turn.listen`.
- **Hand-installed units.** `install.sh --upgrade` writes `dilla-media.service`, `dilla-media-refresh.service`, `dilla-media-refresh.timer` and `/usr/local/libexec/dilla-media-refresh`, runs `daemon-reload` and enables the timer; it leaves an existing `dilla.service` untouched (it needs no change). If you copy units by hand, copy those four files from `deploy/`, `daemon-reload`, and `systemctl enable --now dilla-media-refresh.timer`. Until you do, the old unit still has `PartOf=dilla.service` and `Type=simple`.
- **Check for live calls before you upgrade only when the release needs a restart.** For this release from web3.11 or any web3.12.x, it does not. `dillad media --rooms --config=/etc/dilla/dilla.toml` still lists the live rooms.
- **A media server on the older binary is normal.** After the upgrade `dillad doctor` shows `media_binary` in yellow until the refresh timer has moved it. Look at `journalctl -u dilla-media-refresh` for each restart.
- **Rolling back to web3.12.x** (usually web3.12.4, the release this one replaces; its schema is 23, so `--to=23`). The simplest way is the installer, in this order (the config flag is `--config=`, and `migrate down` needs `--i-know-what-i-am-doing`):

  ```sh
  # 1. Stop both units. Do this first: migrate down must not run under a live web3.13 dilla,
  #    or its kind-3 inserts fail and a crash restart migrates the database back up.
  systemctl stop dilla dilla-media     # ends every live call
  # 2. Public mode only (every tls.mode but behind_proxy): edit /etc/dilla/dilla.toml and remove
  #    turn.listen, and remove turn.public_url if you set it for the opt-in.
  # 3. Take the database down with THIS release's binary.
  runuser -u dillad -- /usr/local/bin/dillad migrate down --to=23 --i-know-what-i-am-doing --config=/etc/dilla/dilla.toml
  # 4. Install the previous release with THIS release's install.sh (the web3.13 asset): only it knows how to
  #    roll back to the old scheme. With both units stopped it needs no --yes.
  sh install.sh --upgrade --version v0.1.0-web3.12.4
  ```

  The installer then writes a `Type=simple` unit and disables the refresh timer, and it refuses before changing anything while a public-mode `turn.listen` is set. By hand instead:

  ```sh
  # 1. Remove a public-mode turn.listen from dilla.toml (every tls.mode but behind_proxy;
  #    an omitted tls.mode counts as public). web3.11 and web3.12.x refuse it. Also remove
  #    turn.public_url if you set it for the opt-in: web3.12.x hands clients that URL verbatim
  #    (internal/dillad/routes.go), so it would keep advertising the dead port while doctor,
  #    which probes 443, stays green.
  # 2. Stop both units. systemctl stop dilla no longer stops dilla-media.
  systemctl disable --now dilla-media-refresh.timer
  systemctl stop dilla-media          # ends every live call; dilla-media goes first so turn.listen is free
  systemctl stop dilla
  # 3. Take the database down with THIS release's binary (only it knows the way down).
  runuser -u dillad -- /usr/local/bin/dillad migrate down --to=23 --i-know-what-i-am-doing --config=/etc/dilla/dilla.toml
  # 4. Put the previous pair back (the `.prev` pair is web3.12.4's, the usual previous release, if this release was installed with `install.sh --upgrade` and nothing was upgraded since) and make the media unit Type=simple again.
  cp -p /usr/local/bin/dillad.prev /usr/local/bin/dillad
  cp -p /usr/local/bin/dilla_core_wasi.wasm.prev /usr/local/bin/dilla_core_wasi.wasm
  # edit /etc/systemd/system/dilla-media.service: Type=notify -> Type=simple, delete NotifyAccess=main;
  # web3.12.x does not send READY=1, so a notify unit waits out its start timeout.
  systemctl daemon-reload
  # 5. Start them again, dilla-media first.
  systemctl start dilla-media
  systemctl start dilla
  ```

  To go below web3.12, use `--to=21` (web3.12's migrations 00022 and 00023 drop `status_msg`, `bio` and device names) as web3.12's notes describe. **The down step drops `mls_pending_proposals.withdrawable`, `withdrawn_at` and `withdrawn_seq`, deletes every kind-3 `withdrawn` handshake row** (the web3.11 and every web3.12.x core refuse a whole page that carries one) **and every withdrawn proposal row.** A withdrawn proposal is deleted, never revived; a client that already dropped it stays consistent with a server that no longer lists it. Nothing else is lost: a call in progress ends, and nothing in `mls_handshakes` other than kind 3 changes.

  **If `migrate down` fails on SQLite,** restore the newest `<db.path>.pre-migration-<unix time>` made by this upgrade, as in web3.12's notes; it loses everything written after the upgrade. **Postgres has no such copy.**

  **What a rollback does not undo.** Tabs that already reloaded into the web3.13 build stay on it until they reload again. Epochs that resumes moved stay moved, and an absence Remove that was withdrawn is not put back. The unit and script files the installer wrote (`dilla-media-refresh.service`, `.timer` and the libexec script) stay on disk, with the timer disabled, and so does the timer's record `/var/lib/dilla-media-refresh/pending`. `dilla-media.service` stays without `PartOf=dilla.service` after either rollback, so on the rolled-back 12.x `systemctl stop dilla` still leaves the media server running. A TURN handoff that moved `turn.listen` into `dilla-media` is gone with it: after the rollback `dillad serve` binds it again. `media.sock`, `api.sock` and `media.json` in the state directory are not used by web3.12.x. The pre-migration copies stay.
- **A page on web3.13 talking to an API rolled back to web3.12.x** gets a 404 on `POST /v1/calls/{call_id}/relay`. That ends that reconnect's credential refresh, and the page rejoins through a fresh call start, which gets fresh credentials from the older API. (A rollback stops `dilla-media`, which ends every call, so this mostly concerns tabs that reconnect afterwards.)
- **The installer's rollback to web3.12.x** logs "rolling back below v0.1.0-web3.13 while dilla-media runs …, which holds turn.listen: stopping dilla-media first, which ends every live call". The installer's own rollback of an upgrade whose API does not start puts the previous pair back and writes the unit for it; when the media server was already restarted onto the new binary, it stops `dilla-media` first so exactly one process holds `turn.listen`. When it cannot prove the database is at a schema the previous binary reads, it stops, leaves the new binary in place and prints the ways out, including setting `Type=simple` for a release below web3.13. A rollback to web3.12.x whose `dilla` then fails to start is itself rolled back: web3.13 is put back with `dilla-media-refresh.timer` enabled again (before this, the timer stayed disabled and the media server never moved onto a newer binary).
- **Non-systemd installs.** There is no `PartOf` and no timer to rely on: restart `dilla-media` and `dilla`, both, after an upgrade, and `dilla-media` first when the new release moves TURN into it.
- **A `dillad` that cannot run under the media unit.** `dilla-media.service` runs nothing but `/usr/local/bin/dillad` (`NoExecPaths=/`, `ExecPaths=/usr/local/bin`). A dynamically linked build fails to start.
- **web3.11's and web3.12's rollback wording changed.** Their notes say `systemctl stop dilla` also stops `dilla-media` because of `PartOf=dilla.service`. That holds only while their units are installed; after an upgrade to web3.13 the unit has no `PartOf`, so a rollback from web3.13 stops both.

## Known limits

- **Public-mode TURN on 443 stays in the API process.** A relayed call in public mode survives an API restart only through the page's fresh credentials (the new route) and a gap of about 19 to 21 s measured in the compat job; set `turn.listen` to move the relay into `dilla-media`.
- **A release that raises `min_sfu_media_level` still ends calls.** The installer says so before it restarts.
- **A rollback below web3.13 ends calls.**
- **The first device back after everyone dropped keeps its place; the others rejoin the same call by a fresh join,** up to about 30 s after the server answers.
- **Every resume moves the epoch by one.**
- **A microphone prompt after an update reload** in browsers that ask every time (Firefox) can delay the rejoin until a click.
- **Firefox A2 is flaky and not understood** (see "Not yet seen"). It runs in the non-required `upgrade-e2e` job, so it does not block pull requests.
- **An update reload just after a long absence can rejoin a call the person left while away.** If a device was asleep or offline for longer than the inactive timeout and the page reloads for an update in the few seconds after it wakes, before it rejoined, the reloaded page puts it back in the call instead of saying "You left the call while away." (`docs/user/voice.md`). Not a regression: a reload before this release recorded no absence either.
- **`--yes` goes away in the next release.**
- **`dillad.prev` after a compatible upgrade** is not the media server's binary: the rollback restarts the media server once, when idle, onto identical code. Harmless.
- The web3.12 known limits still hold, except that calls now survive an upgrade.
