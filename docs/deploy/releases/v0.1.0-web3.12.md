# dilla v0.1.0-web3.12

Released 2026-10-22.

You can now write a status message and a bio, and name your devices; the server stores both readable. GIFs play in the conversation. A computer that was away longer than the AFK timeout no longer rejoins a call by itself, and a call join survives a commit that lands while it reads.

> **The `dillad.prev` swap is not the rollback for this release.** The database moves to schema 23 at the first start, and web3.11 refuses to start on it. Roll back with `migrate down` first, as described in [Operator notes](#operator-notes).

## What's new

### Exercised by tests

The server pieces are proved by Go tests against the real handlers (`internal/api/profile_test.go`, `profile_legacy_test.go`, `device_label_test.go`, `gifs_dim_test.go`), by the store tests (`internal/store/profile_test.go`, `devices_test.go`, `schema_test.go`) and by the migration tests under `cmd/dillad`. The client pieces are proved by unit tests in jsdom, with fake timers and a mocked `IntersectionObserver`. **No browser-suite spec (`e2e/`) covers any feature below**: the only e2e changes in this release make two existing specs less racy.

- **Status message and bio.** Settings → profile has three fields: display name (at most 64 characters), a one-line status message (at most 190) and a bio (at most 500, with line breaks). **save** sends only what changed. The status message shows on your profile card after the presence word, and the bio under your name. `PATCH /v1/accounts/me` answered `501` until now. It takes `[display|null, status_msg|null, bio|null]`: a `null` leaves a field alone and `""` clears it, every given field is checked before anything is written, and one `UPDATE` writes only the given fields, so two devices changing different fields do not overwrite each other. `GET /v1/accounts/me` and each row of the member list gain `status_msg` and `bio` as their last two elements. The route spends the device session's write bucket.
- **The text rule.** A display name, a member nickname, a status message and a bio share one rule, in `internal/auth/profile_text.go` and mirrored in the client (`packages/client-core/src/profile-text.ts`): NFC, trimmed, counted in characters, not only whitespace. It refuses control characters, bidi controls, zero-width and other default-ignorable characters, unassigned, private-use and surrogate code points, and more than 8 combining marks in a row. A line break is refused except in a bio. A joiner is kept where a script or an emoji needs one (Persian, Sinhala, Devanagari and similar scripts, and emoji sequences). Character properties come from the tables of one Unicode version (17.0.0), generated by `scripts/gen-profile-text-tables.mjs`. Only a new or changed text is checked: **a display name stored before this rule is kept as it is** and still reads back.
- **Device names.** Settings → devices has a **rename** button on every live device (this one or a sibling), starting this browser on a suggestion such as "Firefox on Linux". A device shows its name with the first eight characters of its id beside it, and the remove dialogs name the device by both. `PATCH /v1/devices/{device_id}` takes `[label|null]` (`null` clears the name) and answers `204`; the label is 1 to 64 characters under the text rule above, one line; another user's, an unknown or a removed device answers `404`; it spends the device session's write bucket. `GET /v1/devices` gains the label as a seventh element, returned only to the owner. The name is **not** part of the signed device list: the server stores it readable and could change it, which is why the id stays beside it.
- **GIFs play in the conversation.** A GIF attachment of at most 8 MiB plays inline for five minutes from the first time at least half of its card is visible, then goes back to its still. The clock does not restart when the card scrolls out of view and back, and a card that was never in view fetches nothing. Opening a GIF shows it animated, as before. With reduced motion the GIF stays still until it is opened. A still GIF carries a small "GIF" mark. Direct messages use the same card, so a GIF received there plays too.
- **GIF picker tiles keep their shape.** The Giphy search answer carries each preview's width and height; the instance now passes them on only as whole numbers of 1 to 4000, both or neither (`0, 0` when unknown), and the client checks them again. Tiles are sized from them, so a tall GIF is not cropped.
- **The grouped time fits.** The time in the left gutter of a continuation row beside an image-only message is no longer cut off.
- **A call join survives a commit.** When another member commits (a Remove from a reloaded page's sweep, a rotation) between the join's two reads of the call group's GroupInfo and tree, the core refuses the pair with `E_CORE_INPUT`. The join now reads both again, up to 3 reads, instead of failing the call. Three disagreeing reads in a row still fail the join with `E_CORE_INPUT`.
- **No rejoin after a long absence.** A computer that loses its connection during a call (the lid closed, the Wi-Fi gone) and comes back after more than the server's inactive timeout (5 minutes unless the server sets another) no longer rejoins the call by itself: the channel says "You left the call while away." and **join voice** takes you back in. A shorter drop, such as a Wi-Fi blip or a quick sleep, still rejoins by itself. A "Moved to AFK" or "You went AFK on another device." reason still wins, and the rejoin after an upgrade keeps its 2-minute window. On a server without an AFK channel, when the AFK settings cannot be read, and in direct-message calls, a lost call keeps trying to rejoin as before.
- **`dillad` refuses a database that skipped a migration.** `serve`, `migrate status`, `migrate up` and `doctor` now ask goose whether a migration numbered below the database's highest version was never applied (a build that carried a later migration but not an earlier one once ran against it). `serve` and `migrate` then exit with an error that names the missing versions and the `migrate down --to=N` that undoes only the out-of-order ones; `doctor` fails its database leg. Before, comparing only the two highest versions let such a database start.
- **Installer.** `install.sh --upgrade` now says "restarting the sidecar SFU on the new binary; this disconnects everyone in a call, and not every client rejoins" (it used to say connected calls rejoin). It also no longer discards the error output of `migrate status` when it reads the schema version, so a failure there shows its cause. `deploy/install_test.sh` covers the text.

### Also in web3.11, missing from its notes

These were merged before the web3.11 tag (`git log v0.1.0-web3.10.1..v0.1.0-web3.11`), but `v0.1.0-web3.11.md` describes only AFK. They add no migration. They are listed so the record is complete, and the README's "What is not there yet" no longer lists them.

- **Change or set your password** in Settings → sign-in (E1; the route is `POST /v1/auth/password`).
- **Search button on touch devices** (E2).
- **Profile card in direct messages** (E3), with message and compare safety numbers as its only actions.
- **Safety number as a QR code** (E4), shown on request in the compare dialog; nothing scans it.
- **Markdown in messages** (E5).
- **GIFs from Giphy** (E8): a per-server key set by the server's managers, GIFs sent as encrypted attachments; see "GIFs" in the operator guide.
- **`dillad admin device revoke --all`** (E9): signs every device of a person out and deletes their sessions, for a person who lost every device; see the operator guide.

### Not yet seen working on a real instance

Some of this ran in the browser suite: images through the conversation (`conversation.spec`, Chromium), the AFK and late-rejoin flow (`afk.spec`, Chromium), and the join after a reload that the re-read fixes (`voice/reload.spec`, Firefox, 20 of 20). The rest is unit and server tests only. None of it has been watched on real devices against a deployed instance. In particular:

- **The profile and device-name screens** on a real instance with two browsers, including the rename of a sibling device and a status or bio change appearing in another person's member list (it appears the next time that list is read, on a reload or on opening the server).
- **GIF playback** in real Chromium, Firefox and Safari: the five-minute clock, the stop and the return to the still, the memory cost of swapping a large GIF in and out, and reduced motion set in the operating system.
- **Picker tile heights** against live Giphy answers.
- **A long laptop sleep in a real call.** The 1-second liveness ticks, the suspend detection and its 60-second settle window have unit tests with a fake clock, but no real lid.
- **The call-join retry under a real race.** A unit test forces the commit between the two reads; nobody has hit it on a real call.
- **A rollback from schema 23** with real data. The migrations have down steps that the tests run; nobody has rolled a live instance back.
- **Migrations 00022 and 00023 on a long-lived Postgres database.** The store, api and cmd tests ran against Postgres 18.6 in a container on a fresh database; no upgrade of an existing Postgres instance has been watched.

## Operator notes

- **Schema 23.** Migration 00022 adds `status_msg` (at most 190 characters) and `bio` (at most 500) to `users`, both empty for every existing account. Migration 00023 adds a nullable `label` (1 to 64 characters) to `devices`, empty for every existing device. Both are additive.
- **Routes.** `PATCH /v1/accounts/me` answered `501` before and now answers `204`. `PATCH /v1/devices/{device_id}` is new. `GET /v1/accounts/me`, the member list and `GET /v1/devices` gain trailing elements; an older client reads them as absent and keeps working, and a new client reads a missing element as empty. No other route changed. The wire stays at 2.
- **Privacy: the server reads these.** A display name, status message and bio are stored in the clear, and anyone who shares a server with the account reads them. A device name is stored in the clear and the server could change it; only its owner is shown it. None of them is end-to-end encrypted. The user docs and the README say so.
- **Rollback is not the usual `dillad.prev` swap.** The database is at schema 23 after the first start, and web3.11 refuses to start on a database newer than its own migrations. Putting the old binary back as it is leaves it refusing. Take the database down first, **with the new binary** (only it knows the way down), and then reinstall web3.11 with this release's `install.sh`:

  ```sh
  systemctl stop dilla
  runuser -u dillad -- /usr/local/bin/dillad migrate down --to=21 --i-know-what-i-am-doing --config=/etc/dilla/dilla.toml
  install.sh --upgrade --version v0.1.0-web3.11
  ```

  `systemctl stop dilla` also stops `dilla-media` (its unit is `PartOf=dilla.service`), so no call is live and the installer goes on without `--yes`. The down steps drop `devices.label`, then `users.status_msg` and `users.bio`: **every device name, status message and bio is lost**; the devices and accounts are kept, and display names are unaffected.

  **If `migrate down` fails on SQLite,** stop the service and move the pre-migration copy back. The new binary takes `<db.path>.pre-migration-<unix time>` (a `VACUUM INTO` copy) before it migrates (`cmd/dillad/serve.go`, line 195 in this release), when `db.auto_migrate` and `db.pre_migration_backup` are on (both default on) and there is a migration to run. Use the newest copy that the upgrade made; it is the database as it was at schema 21, and an older copy from an earlier upgrade is not what you want:

  ```sh
  systemctl stop dilla
  ls -l <db.path>.pre-migration-*
  rm -f <db.path>-wal <db.path>-shm <db.path>-journal
  mv <db.path>.pre-migration-<unix time> <db.path>
  install.sh --upgrade --version v0.1.0-web3.11
  ```

  The copy **loses everything written after the upgrade**: messages, joins, status messages and bios, device names, away rows. This is the same restore `dillad serve` runs by itself when a migration fails during its own start (`ops.RestoreFile`, which removes the `-wal`, `-shm` and `-journal` files before it renames the copy over the database). **Postgres has no such copy:** the backup is taken only when `db.driver` is `sqlite` (the condition in `cmd/dillad/serve.go`), so on Postgres a failed `migrate down` can be recovered only from a backup you made yourself before upgrading. Dump the database before you upgrade.
- **Upgrading with live calls.** `install.sh --upgrade` still restarts the media server (SFU), which ends every live call, and its message now says so and says not every client rejoins. As in web3.11 it refuses while a room has participants unless you pass `--yes`. The plan for calls that survive an upgrade is in progress and **is not in this release**.
- **A database that skipped a migration now stops `serve`.** If `dillad serve` or `migrate` reports "missing migration …" (or `doctor` fails its database leg), follow the error: stop dilla, run `dillad migrate down --to=N --i-know-what-i-am-doing` as it says, then start a `dillad` that carries every migration. On SQLite the pre-migration copy is the fallback, as above.
- **Nothing new in `dilla.toml`, and no new port.**
- **Client build tooling moved** (vitest 4, vite 7.3.7, storybook 9.1.21 and others, for npm advisories). It changes how the bundle is built, not what an operator runs.
- **Check `dillad media --rooms` immediately before the restart.** As in web3.11, the answer goes stale; the installer runs it itself.
- **The new browser client comes inside the `dillad` binary.** Open tabs pick up the new build and reload.

## Known limits

- **Profile text is not end-to-end encrypted,** and the server can change a device name; a client shows the id beside it for that reason.
- **A person's new status or bio shows to others the next time their member list is read,** which is when they reload or open the server. It is not pushed.
- **No avatar picture.** A profile is a name, a status message and a bio.
- **An old display name or nickname is kept as it is,** even if it would be refused today; it is checked only when it changes.
- **A rollback to web3.11 discards every status message, bio and device name.**
- **A GIF over 8 MiB, one that fails to open, and any GIF under reduced motion stay still** until opened. After five minutes a GIF goes back to its still until opened again.
- **A lost call still rejoins by itself** after an absence shorter than the AFK timeout, in a server without an AFK channel, and in a direct-message call.
- **The join retry is bounded** at 3 reads of the pair. A group that keeps changing under the join fails it with `E_CORE_INPUT`.
- **Calls do not survive an upgrade.** The SFU restart ends them.
- The web3.11 known limits still hold.
