# dilla v0.1.0-web3.12.3

Released 2026-10-22.

This patch changes the browser client and its core. A message held because of its sender's device list now says why and what would open it. A message from a device its sender removed is final. A timestamp no longer runs under images. Nothing about messages, keys or calls changes on the wire.

## What's fixed

- **A held message now says the real reason it can't be read.**
  - **Before:** a message from a device that wasn't on its sender's signed device list kept saying it was "waiting for the list", even after the list had been read and had refused that device. That asked the reader to wait, when what opens it is the sender adding the device.
  - **Now:** two messages, so operators can grep for them before and after:
    - device never added: "Sent from a device that is not on the sender’s device list. Ask them to add it to their account; the message opens once they do."
    - device removed: "Sent from a device the sender removed from their account. It will not open."
- **A removed device's messages are final.** When a sender's newest signed device list marks a device as removed, the core gives its held messages the new reason **`E_DEVICE_REVOKED`** and discards the ciphertext it kept for them. No later list releases them.
  - **Unchanged:** a message from a device that was simply never listed is still kept, and opens if the sender adds that device.
  - **Not forgeable by the server:** only the cached, pinned list can mark a device as removed, and a list rollback is refused. A server can't fake a revocation.
- **A grouped message's hover time fits its column.** Hovering a grouped message from an earlier day showed the full date ("Oct 21, 2026, …"), which ran under the message's image or GIF.
  - The column now shows the time of day only, with the full date in its tooltip.
  - The day divider above already names the day.
  - The column also clips its text, so a long local time format can't run under images either.
- **Tests:** device-list trust gained negative tests. Each refusal was shown to fail with its guard removed.

## Operator notes

- **No server change.** There is nothing to configure, and no route or migration changed. The new client and core come inside the `dillad` release, so it is still a `dillad` upgrade: `install.sh --upgrade --version v0.1.0-web3.12.3`. Open tabs pick up the new build and reload.
- **Upgrades still end live calls.** The installer still restarts the media server (SFU). The work that lets a call survive an upgrade is still in progress and is **not** in this release. Run `dillad media --rooms --config=/etc/dilla/dilla.toml` immediately before the upgrade, and upgrade only when it reports `no live rooms`.
- **Rolling back to web3.12.2** is the usual `.prev` swap, since no schema, store layout or wire changed:

  ```
  systemctl stop dilla
  cp -p /usr/local/bin/dillad.prev /usr/local/bin/dillad
  cp -p /usr/local/bin/dilla_core_wasi.wasm.prev /usr/local/bin/dilla_core_wasi.wasm
  systemctl start dilla
  ```

  After the rollback, a message already marked `E_DEVICE_REVOKED` shows web3.12.2's generic "could not be read" row. Its ciphertext is gone either way. A message relabelled `E_DEVICE_UNLISTED` behaves as it did in web3.12.2.
  The `.prev` pair is web3.12.2's only if this release was installed with `install.sh --upgrade` and nothing was upgraded since.

## Not yet seen

- **The revoked case in a real browser.** It is covered by core and client tests, and the "device removed" message was checked by unit test only. No browser test revokes a device.

## Known limits

- The web3.12 known limits still hold.
- Under a heavily loaded single CPU, the first message in a channel can stay "sending…" for a long time. This has a different cause, which has not been looked into yet.
