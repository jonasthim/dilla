# dilla v0.1.0-web3.7

## What's new

- **A phone app shell.** At phone width dilla has four tabs at the bottom: Servers, DMs, Activity and You. Opening a
  conversation hides the tabs to leave room for the composer, and the system back button returns you to where you were.
  There is no status bar on a phone. A call in progress shows as a call bar above the tabs, with the controls you need
  and a way back to the call. Every phone control is at least 44 by 44 pixels. Text fields no longer make the page zoom
  when you tap them, and pinch zoom still works. The desktop layout is unchanged.
- **Slow mode works in end-to-end encrypted channels.** The host now enforces slow mode and the **send messages**
  permission on posts. A refused post says how long to wait, and the composer shows a countdown. Members with the
  **bypass slow mode** permission skip the wait. DMs are not checked.
- **Announcement channels.** A channel can be created as an announcement channel, where only members with send
  rights can post and everyone else can read and react.
- **Public threads.** Reply to a message in a thread. On desktop the thread opens in a side column; on a phone it opens
  as a sheet. A thread's replies stay out of the main timeline. Reading a channel marks its thread replies read.
  Thread replies notify you, and a notice in Activity opens its thread. Threads exist only in server channels, not in
  DMs.
- **Search on phones.** The search control is in the channel menu and in the server menu.
- **No ghost after a reload during a call.** Reloading the page used to leave a stale tile of you in the call. The
  page now clears its old place when it starts, and a late leave from the old page no longer cuts the new one.
- **`dillad doctor`** warns about the WebAuthn origin only when `rp_origins` does not contain `https://<domain>`, and
  prints a summary line at the end (not with `--quiet`).
- **`dillad admin user list`** has a FACTORS column, and `dillad admin user show` lists each second factor.
- **Recovery-key step.** If someone types a backup code where the recovery key belongs, the step now says so and
  points them to the right place.
- **Sign-in and second-factor fixes from web3.6.** Password change, authenticator confirmation, the sign-in code and
  backup codes now hold up when two requests arrive at the same moment (a code or backup code works once), and a
  password change checks its confirmation before it spends it. A valid authenticator code is no longer rarely
  refused: a code is matched at the lowest unused counter.
- **The voice dock** no longer repeats the call controls on desktop while the call stage is open.
- **Icons are same-origin files.** The interface icons now load as files from the server itself, so they work under
  the unchanged content security policy.

## Operator notes

Upgrade as usual with `install.sh --upgrade`. Then ask every user to reload every open tab (see below).

### Database: migration `00018_message_class`

Database schema 17 becomes 18. The migration adds a nullable `class` column to `mls_app_messages` and a new table,
`slowmode_marks`, which holds each person's last accepted post time per channel so that pruning old messages never
resets slow mode. It changes no existing row and is quick on large tables.

**Rolling back the database is safe.** Going down from 18 to 17 drops the `class` column and the `slowmode_marks`
table and keeps every message; slow-mode waits restart. Use the **new** binary to go down, then put the old binary back:

1. `systemctl stop dilla`
2. `runuser -u dillad -- /usr/local/bin/dillad migrate down --to=17 --i-know-what-i-am-doing --config=/etc/dilla/dilla.toml`
3. Put `dillad.prev` and `dilla_core_wasi.wasm.prev` back over `dillad` and `dilla_core_wasi.wasm`.
4. `systemctl start dilla`

`install.sh --upgrade` does this by itself when the new binary fails to start. The full procedure is in the deploy
guide under "Rolling back by hand".

### Browser data: client store schema 5 (refuse and restore)

A browser that opens web3.7 moves its local store from schema 4 to 5. This is **one-way, and a rollback of the server
alone is not safe for that browser**: if you roll the server back to web3.6, that browser shows the "too old" screen
(data version 5 found, 4 supported) and does not open the app. To recover, either redeploy web3.7, or clear the
site's data in that browser and sign in again with the recovery key. Clearing the data removes the messages that
browser held locally. A browser that never opened web3.7 is not affected. Tell your members before you roll back.

### Pages open during the upgrade

Every user should reload every open tab. A page loaded before the upgrade keeps working, but it speaks the older
upload format:

- The host accepts these legacy two-element uploads until web3.8, which refuses them. They are checked for **send
  messages** but not for slow mode, so a crafted legacy upload skips slow mode for this one release. Slow mode applies
  to anyone running web3.7 code.
- Such a tab cannot react, edit, delete or pin in a channel where its user lacks send rights until it reloads.
  The same applies in an announcement channel.

### What the host learns

For each end-to-end encrypted upload the host now learns whether it is a post or something else (a fold: an edit,
a reaction, a delete and so on). It needs this to apply slow mode and the send permission. It still cannot read any
content. See `protocol/08`.

### Threads on older browsers

Replies that a web3.6 browser stored are not moved into threads after the upgrade (there is no backfill), so the
same thread can look different on an old and a new device. Messages sent from web3.7 on show the same everywhere.

### Other operator-visible changes

- `dillad doctor` and `dillad admin user list/show` change as described above. Scripts that parse the old doctor or
  list output may need an update (a new summary line, a new FACTORS column).
- The browser build's WebAssembly budget is now 3.6 MB (it was 3.5 MB); the shipped core is about 3.52 MB.
- On desktop the voice dock hides its controls while the call stage is open. No setting changes.
- No new configuration keys, permission bits, error codes or gateway operations.

## Known limits

- A moderator whose only role is their top role cannot create an announcement channel. The fix needs a server change
  to the permission rules and is not part of this release.
- If the member list has not loaded, a person who cannot post may still be allowed to create an announcement channel;
  the host then lets them make it but not post in it.
- Activity starts from "since this tab opened". It does not list earlier mentions or replies.
- There is no per-thread unread marker: reading a channel marks all its thread replies read.
- Threads show up to 200 replies and do not page further.
- A reply typed in a thread but not yet sent can appear in the main timeline after a reload, until it is stored.
- A first post made before a channel learns its new slow-mode value shows no countdown (the message is still held
  and sent).
- Rotating a phone remounts the open conversation and loses scroll position and focus.
- Two posts queued in the same second can arrive in swapped order if the page reloads before they are sent.
