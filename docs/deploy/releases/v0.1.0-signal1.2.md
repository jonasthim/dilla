# dilla v0.1.0-signal1.2

A hotfix release on top of [v0.1.0-signal1.1](v0.1.0-signal1.1.md), PR #130. It fixes two production problems that
showed up after signal1.1, the Bot tripping the instance's rate limits and music never playing, and carries two
delivery-service fixes. The release includes `dillad` (with the web client), `dillabot`, their matching core modules,
installers and checksums.

## What's fixed

- **The Bot no longer trips the rate limits.** signal1.1 made Bot interaction admissions about 2000× faster, which took
  away what had been slowing the Bot down. It then went over the instance's write limit (2/s). Each 429 paused its event
  dispatch for about 30 s, and commands such as /play said "the resulting state could not be confirmed".
  - A rate limit is now always transient for the Bot. It waits for the server's Retry-After (or backs off with jitter)
    within each request's deadline, and a rate-limited event stays pending. It is not dropped and does not count toward
    the event age limit. Dispatch never pauses for a rate limit.
  - The Bot paces its own requests below the instance limits, per class, matching the server's: write, read, message,
    commit, proposal and key-package. The rates can be overridden in `/etc/dillabot/bot.toml` under `[rate_limits]`
    (`write_per_second`, `write_burst`, `read_per_second`, …); zero or absent means the default.
  - Idle background polling backs off from 1 s to 30 s. Commands from the gateway are still answered right away.
  - A person's command never waits behind the Bot's background work. Its requests go first within the same limits, and
    background passes give way and resume right after. Announcements, reminders and poll closing still run on every
    pass, and a pass that has given way too long (the reconcile interval plus 60 s) finishes without giving way.
- **/play plays.** The Bot had never joined a call:
  - YouTube **Share** links (`youtu.be/<id>?si=…`) and several other common forms were rejected before YouTube was
    contacted. The browser then reported "could not be confirmed" and never asked the Bot to start. Share links, `&t=`,
    `&list=` on a video, `music.youtube.com`, `/live/`, `/shorts/`, `/embed/` and links without `https://` are now
    accepted, and rebuilt into the canonical `https://www.youtube.com/watch?v=<id>` before yt-dlp sees them.
  - A failed music operation now shows a definite message ("Glenn couldn't load that track. Try again or try another
    link."; for other music controls "Glenn couldn't do that right now. Try again.") instead of "could not be confirmed".
  - When a call join hits a conflict, the Bot re-reads the call and retries instead of staying stuck. Forgetting a call
    group now also discards the Bot's pending join, create or commit records for it in the end-to-end encrypted core
    (security-reviewed), so a failed join no longer blocks every later join in that call.
- **Every refused music operation is logged**, with a reason class. A failed YouTube lookup logs yt-dlp's or the
  sandbox's error output on one line, truncated to 512 bytes, with the link, the video ids and the search text redacted.
  `dillabot doctor --youtube` now also starts the real sandbox (`youtube_sandbox` OK or FAIL).
- **A channel's only member is never removed by the commit watchdog.** When the one person who could commit took more
  than about 6 s (for example while creating several channels right after installing the Bot), the watchdog removed
  them, and nobody was left who could commit. That device is now kept, and asked again with a back-off from 2 s to 60 s.
  (protocol/02, invariant 7, amended.)
- **Closed call groups no longer keep a pending proposal forever.** Ending a call left its last Remove pending, and
  nothing voided it (58 such groups on the Homelab instance; nobody was affected). The 1-minute sweep now voids live
  proposals of closed groups, so the backlog clears itself within a minute of the upgrade. The
  `dilla_ds_proposals_outstanding` gauge is set from the database at start and no longer goes negative.

## Versions and compatibility

| Server database schema | **54** | 53 |
| Browser client store schema | 13 | 13 |
| Negotiated wire version | 4 | 4 |

## Database migrations

| Migration | What it does |
|---|---|
| `00054_live_proposals` | Adds a partial index on `mls_pending_proposals(group_id) WHERE void_at IS NULL`, used by the new sweep. Its down migration drops it. |

## Deploy order

1. Back up the server database and config. Check that no call is live (`dillad media --rooms
   --config=/etc/dilla/dilla.toml`): the upgrade restarts media and ends calls.
2. **Upgrade `dillad` first** with `install.sh --upgrade`. Confirm `dillad migrate status` shows 54, the service is
   healthy, and a browser signs in.
3. **Ask everyone to reload their open tabs** (the new music messages and link handling are in the web client).
4. **Then upgrade `dillabot`** with `install-bot.sh --upgrade`, and run
   `sudo -u dillabot dillabot doctor --config=/etc/dillabot/bot.toml --youtube`.
5. If you raised `[limits.rate] write_per_second` in `dilla.toml` as a stopgap for the Bot's 429s, put it back once
   both are upgraded.

Rolling back to signal1.1 is possible: wire and the browser store are unchanged, and `migrate down --to=53` only drops
the index. A signal1.1 Bot on this server behaves as before (it can trip the rate limits again).

## Known limits

- An automated test that the Bot really becomes a member of a call's encrypted group is still missing (the harness is
  planned for signal2). The first `/play` after this upgrade is the first real join on a live instance; its failures
  are logged.
- `/play` is still two steps in the browser (add the track, then start). Starting an idle queue from the Bot itself is
  a later change.
